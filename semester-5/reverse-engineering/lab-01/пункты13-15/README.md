# Пункты 13–15 — упаковка и анализ UPX

Здесь находятся `protected_for_upx.c`, упакованный `crackme_protected_packed.exe` и входные файлы для положительного теста. Неупакованный образец **той же версии** — [`../binaries/crackme_for_upx.exe`](../binaries/crackme_for_upx.exe).

Сравнивать с `crackme_protected.exe` некорректно: у него другая реализация поиска области CRC. Исходный `main.c` сохранён отдельно и не изменён.

## 13. Упаковка

Использован UPX **5.2.1** для Windows x64, стандартный режим. Упакованный файл создан отдельно, без перезаписи исходного EXE:

```powershell
# Из корня лабораторной; каталог build должен существовать
upx -o .\build\crackme_packed.exe .\binaries\crackme_for_upx.exe
upx -t .\build\crackme_packed.exe
```

Для запуска сохранённого образца:

```powershell
.\пункты13-15\crackme_protected_packed.exe
Get-Content .\пункты13-15\serial.txt
```

Правильный пароль — `lab1pass`. Для `Hello 123` с LF ожидается `KEY$0000001307$`. Выходные файлы создаются рядом с EXE и игнорируются Git.

### Зачем адаптирована CRC

Обычная защищённая версия ищет код по секции `.pchk`. После UPX таблица секций перестраивается и такого имени нет. Поэтому в этой версии `check_crc()` получает адрес `check_password` напрямую и проверяет `PASSWORD_CODE_SIZE = 0xA4` байта.

Проверка выполняется после восстановления кода распаковщиком. Эталон `0x8D686F4F` не изменён: CRC не отключалась. Длина `0xA4` и эталон относятся к конкретной сборке; при изменении кода или toolchain их нужно перепроверить.

## 14. Точка входа и OEP

Порядок выполнения:

```text
Загрузчик Windows
    → новый entry point распаковщика UPX
    → восстановление кода и необходимых импортов
    → переход к OEP исходной программы
    → стартовый код C runtime
    → main()
```

Для сохранённых образцов:

- Новый `AddressOfEntryPoint`: RVA **`0x22A40`**, секция `UPX1`.
- Завершающий переход распаковщика: RVA **`0x22C9B`**, байты `E9 85 E4 FD FF`.
- Адрес следующей инструкции: `0x22CA0`; знаковое смещение перехода: `-0x21B7B`.
- Цель: `0x22CA0 - 0x21B7B = 0x1125`.
- **OEP = RVA `0x1125`**, вход `mainCRTStartup`, не сама `main`.

В x64dbg адрес вычисляют как фактическая база модуля + RVA. На завершающем `jmp` можно поставить точку останова и шагом `F7` увидеть переход к OEP. Дальнейшее выполнение защищённой программы под отладчиком может завершиться отказом anti-debug.

Распаковка `upx -d` отдельной копии восстанавливает PE с исходной точкой входа и секцией `.pchk`. Это не обещание побайтовой идентичности исходному файлу: в проведённом эксперименте SHA-256 распакованного EXE отличался, хотя код и работоспособность восстановились.

## 15. Сравнение сохранённых образцов

| Параметр | До UPX | После UPX |
| --- | ---: | ---: |
| Размер файла | 117 296 байт | 71 728 байт |
| Число PE-секций | 20 | 3 |
| Точка входа, RVA | `0x1125` | `0x22A40` |
| Энтропия всего файла | 5,3538 бит/байт | 6,0000 бит/байт |

Размер уменьшился на 45 568 байт, или 38,85 %. В упакованном PE находятся `UPX0`, `UPX1` и `.rsrc`:

- `UPX0`: виртуальный размер 110 592 байта, сырых данных в файле нет; область предназначена для восстановления содержимого в памяти.
- `UPX1`: 28 160 байт сырых данных, энтропия этой области около 7,8525 бит/байт.
- `.rsrc`: ресурсы, 2 048 байт сырых данных.

У обоих файлов есть одинаковый overlay размером 41 008 байт. Поэтому энтропия всего EXE заметно ниже энтропии сжатой области `UPX1`.

Энтропия Шеннона вычисляется по частотам байтов: `H = −Σ pᵢ log₂(pᵢ)`. Высокое значение характерно для сжатых или зашифрованных данных, но само по себе не доказывает ни шифрование, ни вредоносность файла.

UPX усложняет первоначальный статический анализ, но не обеспечивает секретность: доступна распаковка, а исходные инструкции восстанавливаются в памяти при запуске.
