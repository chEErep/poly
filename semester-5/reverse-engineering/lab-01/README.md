# Лабораторная работа № 1 — реверс-инжиниринг и защита ПО

Учебная программа **crackme** на C для Windows x64. Сначала реализована обычная проверка пароля и анализ текстового файла, затем добавлены защитные механизмы, выполнен бинарный обход проверок и исследована упаковка UPX.

Задача работы — сравнить исходную и защищённую версии и на практике увидеть, что именно усложняет анализ, а какие проверки можно обойти. Это учебный пример, а не система лицензирования или надёжное средство защиты секретов.

## Что делает программа

1. Читает первую строку `password.txt`, расположенного рядом с EXE.
2. Проверяет пароль. Учебный правильный пароль — `lab1pass`.
3. Анализирует соседний `input.txt`: размер в байтах, строки, слова, символы, цифры, пробелы, строчные и заглавные буквы.
4. Создаёт `report.txt` со статистикой и `serial.txt` с номером вида `KEY$xxxxxxxxxx$`, где `x` — десятичная цифра.

Серийный номер вычисляется из статистики файла: для одинаковых входных байтов результат одинаковый. Это не случайный ключ и не цифровая подпись.

Файлы ищутся **в каталоге EXE**, а не в текущем каталоге терминала. При неверном пароле программа завершается с кодом `1`; при успешной работе — с кодом `0`.

В `binaries/`, `пункт12/` и `пункты13-15/` лежат входные файлы для запуска соответствующих образцов. В `пункт12/password.txt` намеренно записан **неправильный** пароль `wrongpass`.

Готовые EXE сохранены намеренно: адреса, размер проверяемого кода и бинарные патчи относятся к конкретным сборкам. После новой компиляции побайтовое совпадение не гарантируется. Отчёты Word, скриншоты, настройки IDE и временные каталоги в репозиторий не включены. Генерируемые `report.txt` и `serial.txt` также не отслеживаются Git.

## Сборка

Нужны **Windows x64, CMake 3.20+, Ninja и MinGW-w64 GCC**. Для анализа использовались IDA, x64dbg и Detect It Easy; для обычной сборки они не нужны. MSVC не является прямой заменой: защищённые исходники используют атрибуты GCC, `<cpuid.h>` и GNU inline assembly.

Сохранённые образцы собирались MinGW GCC **13.1.0** из CLion. Для защищённых целей заданы `-O0` и `-fno-toplevel-reorder`. Debug-сборки содержат отладочную информацию; отключение оптимизации не означает удаления символов.

### Через CLion

1. Открыть эту папку как CMake-проект.
2. Выбрать toolchain **MinGW x64** и профиль **Debug**.
3. Собрать нужную цель: `crackme`, `crackme_protected` или `crackme_for_upx`.
4. Скопировать `examples/password.txt` и `examples/input.txt` в каталог получившегося EXE, обычно `cmake-build-debug`.
5. Запускать через **Run**, если не требуется намеренно проверить anti-debug. Запуск через **Debug** подключает отладчик и может вызвать отказ защищённой версии.

### Через терминал

Команды выполняются из этой папки в PowerShell. CMake, Ninja и GCC должны быть доступны через `PATH`:

```powershell
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build
Copy-Item .\examples\password.txt, .\examples\input.txt -Destination .\build
.\build\crackme.exe
```

Если в системе несколько компиляторов, укажите нужный через `-DCMAKE_C_COMPILER="полный путь к gcc.exe"`. Каталог `bin` выбранного MinGW всё равно должен быть в `PATH`: он нужен и для зависимостей компилятора. Каталог сборки старого проекта переносить не нужно: CMake хранит в нём абсолютные пути.

## Быстрая проверка без пересборки

Из корня лабораторной:

```powershell
# Исходная версия
.\binaries\crackme.exe
Get-Content .\binaries\report.txt
Get-Content .\binaries\serial.txt

# Защищённая версия, без отладчика
.\binaries\crackme_protected.exe

# Бинарный патч защищённой версии: рядом уже лежит wrongpass
.\пункт12\crackme_protected_patched.exe

# Упакованная версия с правильным паролем
.\пункты13-15\crackme_protected_packed.exe
```

Для сохранённого `input.txt` (`Hello 123` и перевод строки LF) незащищённая версия выводит:

```text
File analysis report
File size: 10 bytes
Lines: 1
Words: 2
Characters: 9
Digits: 3
Spaces: 1
Lowercase letters: 4
Uppercase letters: 1
```

В защищённых версиях строка размера записывается как `File size: 10`, без суффикса `bytes`; значения счётчиков совпадают. Серийный номер: `KEY$0000001307$`. Если редактор заменит LF на CRLF, размер станет другим, поэтому изменится и номер.

Для отрицательного теста скопируйте EXE и входные файлы в отдельную папку, замените пароль и запустите программу. Смотрите сообщение, `$LASTEXITCODE` и наличие **новых** выходных файлов. Неудачный запуск не удаляет старые `report.txt` и `serial.txt`, поэтому оставшиеся результаты прошлого запуска не доказывают успех текущего.

## Какие защиты добавлены

| Приём | Где смотреть в коде | Что происходит |
| --- | --- | --- |
| Маскировка строк XOR | массивы `E_*`, `decode`, `say`, `open_file` | Строки хранятся как байты, восстанавливаются при использовании с ключом `0x5A` |
| Проверка пароля без открытого эталона | `check_password` | Побайтовое сравнение с XOR-массивом и проверка точной длины |
| Вторая и ложная проверки | `check_password_sum`, `false_check` | Взвешенная сумма и отвлекающий пароль `fakepass` |
| Контроль целостности | `crc32`, `check_crc`, секция `.pchk` | Сравнение CRC-32 машинного кода проверки пароля с эталоном |
| Связь проверок с результатом | `stages`, `make_serial` | Для формирования serial требуется итоговое значение `31` |
| Anti-debug | `debug_detected` и помощники | `IsDebuggerPresent`, `CheckRemoteDebuggerPresent`, время цикла и поиск `0xCC` в начале проверяемой функции |
| Anti-disassembly | `disasm_jump`, `disasm_branch`, `disasm_overlap` | Переходы через ложные байты, предсказуемое ветвление и перекрывающаяся трактовка инструкций |
| Anti-VM | `vm_cpuid`, `vm_mac`, `vm_firmware`, `vm_detected` | Признаки гипервизора, MAC-префиксы и маркеры SMBIOS; отказ требует `firmware && (cpu || mac)` |
| Самомодифицирующийся код | `change_code` | Выделенная область памяти исполняет `mov eax, 7; ret`, затем после изменения операнда возвращает `9` |
| Обфускация потока управления | `run_flow`, `FlowStep`, `step_*` | Косвенные вызовы из таблицы; порядок шагов `0 → 2 → 1`, состояние скрыто XOR |

### CRC и совместимость с UPX

В `protected_main.c` машинный код `check_password` вынесен в `.pchk`. `check_crc()` читает таблицу секций загруженного PE и проверяет `VirtualSize` байтов по адресу `base + VirtualAddress`.

В сохранённых сборках размер этой области — `0xA4` (164 байта), эталон CRC-32 — `0x8D686F4F`. Используется полином в отражённом представлении `0xEDB88320`, начальное значение `0xFFFFFFFF` и финальная инверсия.

После UPX отдельной записи `.pchk` в таблице секций нет. Поэтому `protected_for_upx.c` проверяет восстановленный в памяти код **по адресу функции** и длине `PASSWORD_CODE_SIZE`, а не ищет секцию по имени. Контроль CRC не отключён.

**Важно при пересборке:** если код функции или компилятор изменились, старые CRC и размер могут не подходить. Ошибка `Error: protection check failed.` в таком случае не означает, что EXE не собрался. В обычной защищённой версии есть режим получения эталона: при `EXPECTED_CRC == 0` функция печатает рассчитанное значение и завершает проверку отказом. После обновления эталона требуется пересборка. Для UPX-варианта дополнительно перепроверяют длину машинного кода: у указателя на функцию нет встроенной информации о её размере.

### Ограничения

- XOR с постоянным ключом — обратимая маскировка, а не надёжное шифрование.
- CRC контролирует выбранную область, а не весь EXE и не входные файлы. Она не обеспечивает криптографическую подлинность; можно изменить саму проверку или эталон.
- Взвешенная сумма пароля может иметь коллизии. Условие `stages == 31` связывает проверки с результатом, но также поддаётся патчу.
- Anti-debug и anti-VM — эвристики, возможны обходы и ложные срабатывания. Hyper-V/VBS может присутствовать и на физическом компьютере; одного CPUID-признака здесь недостаточно для отказа.
- Анализ `input.txt` побайтовый: `characters` не включает CR/LF, `spaces` считает только обычный пробел, слово — последовательность непробельных байтов. Подсчёт регистра рассчитан на ASCII / стандартную C locale, а не на полноценный Unicode-текст.
- Пути обрабатываются через ANSI WinAPI и ограничены `MAX_PATH`. Пример не решает все вопросы Unicode-путей и длинных имён.
- EXE может быть помечен антивирусом из-за сочетания упаковки, anti-debug и исполнения изменяемого кода. Не нужно глобально отключать защиту системы ради запуска; используйте контролируемую учебную среду.

## Бинарный анализ и упаковка

- **IDA:** строки, ссылки на них, функции, граф потока управления и сравнение машинного кода.
- **x64dbg:** регистры, точки останова, переходы, проверка патча и переход распаковщика к OEP.
- **Detect It Easy:** формат PE64, секции, компилятор, упаковщик и энтропия.
- **UPX:** упаковка, проверка и распаковка отдельной копии EXE.

Упаковка сохранённого образца, если `upx.exe` доступен через `PATH`:

```powershell
# Пишем в новый файл, не перезаписывая сохранённый образец
upx -o .\build\crackme_packed.exe .\binaries\crackme_for_upx.exe
upx -t .\build\crackme_packed.exe

# Для запуска файлы должны лежать рядом с новым EXE
Copy-Item .\examples\password.txt, .\examples\input.txt -Destination .\build
.\build\crackme_packed.exe
```

Каталог `build` должен существовать; если проект не собирался, его можно создать через `New-Item -ItemType Directory -Path build`. При повторной упаковке выбирайте новое имя выходного файла. Сохранённый упакованный образец создан UPX **5.2.1**.
