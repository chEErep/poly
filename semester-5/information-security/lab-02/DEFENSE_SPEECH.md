# Защита лабораторной 2 Служба резервного копирования Windows

Материал для единой сдачи всей лабораторной. Автоматическое обновление ZIP реализовано.
Основное на защите - объяснить назначение компонентов и показать результат.
Полный порядок команд находится в FIRST_SHOW.md; код разбирать для этого сценария не нужно.

## 1 О чём работа и что сделано

Нужно написать службу Windows для резервного копирования. Она работает без пользовательского
окна и читает настройки из файла: исходная папка, путь к ZIP и маски/имена файлов.
Служба обрабатывает подпапки, автоматически учитывает изменения выбранных файлов
и управляется собственными командами и стандартной оснасткой «Службы».

Реализованы все девять требований: конфигурация, первая копия, маски * и ?, ZIP,
архивация библиотекой внутри процесса, автоматическое обновление, свой SCP,
управление через SCM и UNC-пути. Состояние проверок описано в VERIFICATION.md.

Простая схема работы:

1. Пользователь через SCP просит SCM запустить службу.
2. SCM запускает отдельный процесс службы.
3. Служба читает backup.ini и создаёт первую копию.
4. После паузы проверяет выбранные файлы во всех подпапках.
5. Если имена, размеры и содержимое совпадают с ZIP, архив не переписывает.
6. При различиях создаёт актуальный ZIP и заменяет файл по прежнему пути.
7. По запросу Stop освобождает ресурсы и сообщает SCM об остановке.

Пауза по умолчанию 2 секунды. Время проверки и архивации добавляется к задержке.
Сравниваются сами байты: обнаруживается правка той же длины даже с сохранённой датой.
Файлы читаются порциями. Во время паузы поток ожидает событие остановки, без пустого цикла.

Новая копия сначала записывается во временный ZIP рядом с основным. После успешного
закрытия он заменяет backup.zip. При блокировке или временном сбое старая копия
сохраняется, служба пишет RETRY и повторяет попытку. Переименование и удаление тоже
отражаются в актуальном снимке. Истории версий, VSS и шифрования нет.

## 2 Подготовка перед преподавателем

Все действия выполняются внутри Windows 10 в виртуалке. Открыть PowerShell
администратора, Проводник и services.msc. Перейти в C:\BSITLab2.
Отображаемое имя обновлённой службы - BSIT Lab 2 - Backup, служебное - BSITLab2Backup.

Обновить EXE через update-demo.ps1 из актуального пакета. Для начала показа с отсутствующей
службой предварительно выполнить stop и remove. Исходные документы и ZIP не удалять.
Закрыть прошлые просмотрщики архива. Если после репетиции уже есть новый TXT, для показа
можно создать другое новое имя, например новый2.txt.

В начальном наборе выбираются 12 файлов: по три в корне и на каждом из трёх уровней.
После добавлений число увеличивается. Свежая строка Backup ready означает готовность
первой копии, Backup updated - автоматическое обновление. RUNNING этого не доказывает.

## 3 Полный текст выступления

В квадратных скобках действия. Остальное можно говорить преподавателю.

Я показываю вторую лабораторную работу - службу Windows для резервного копирования
файлов в ZIP и собственную программу управления этой службой.

Служба выполняет фоновую задачу под управлением SCM - менеджера служб Windows.
Управляющая часть моей программы, SCP, передаёт ему команды установки, запуска,
остановки и удаления регистрации. В моей программе эти режимы находятся в одном EXE.

[Показываю, что службы пока нет. Выполняю .\backup_service.exe install, обновляю список F5.]

Служба появилась в системе, но ещё остановлена. Установка регистрирует имя службы,
путь к EXE, тип запуска и учётную запись. У моей службы запуск ручной, отдельный
процесс и учётная запись LocalSystem. Установка и запуск - отдельные действия.

[Открываю backup.ini.]

Здесь source задаёт исходную папку, archive - путь к ZIP, строки mask - правила выбора,
а interval_seconds - паузу между проверками. Сейчас пауза равна двум секундам.

Пути записаны в формате UNC. localhost означает саму виртуалку, C$ - административный
общий ресурс диска C. Права проверяются для учётной записи выполняющейся службы.

Заданы три правила: все TXT-файлы, report_?.docx и конкретное имя demo.exe.
Звёздочка означает любое число символов, включая ноль; вопросительный знак - ровно один.
Достаточно совпадения хотя бы с одним правилом.

[Показываю source и папка1\папка2\папка3.]

Программа обходит исходную папку вместе с подпапками. report_1.docx подходит
под наше правило, report_12.docx не подходит: после подчёркивания два символа.
В начальном наборе на каждом уровне выбираются три файла, всего двенадцать.

[Выполняю .\backup_service.exe start. Показываю «Выполняется» и свежий Backup ready в журнале.]

SCM запустил процесс службы. Она прочитала настройки и создала первую копию.
Архив формирует библиотека miniz внутри процесса. Отдельная программа-архиватор
не запускается. Структура подпапок сохраняется благодаря относительным именам в ZIP.

[Открываю backup\backup.zip, показываю файлы и вложенность. Закрываю просмотрщик ZIP.]

Теперь покажу автоматическое обновление без остановки и перезапуска службы.

[В исходной папке открываю заметка.txt, дописываю «Изменено для защиты», сохраняю и закрываю.
В source\папка1\папка2\папка3 создаю новый TXT с текстом «Новый файл» и сохраняю.]

Служба периодически сравнивает выбранные исходные файлы с архивом. При отличиях
автоматически обновляет резервную копию по тому же пути.

[Дожидаюсь свежей строки Backup updated. Заново открываю тот же backup.zip.
Показываю изменённый текст и новый файл в третьей вложенной папке.]

Изменения попали в прежний настроенный архив без ручного запуска копирования.
Служба всё это время продолжала работать. Внутри создаётся временный ZIP, который
заменяет основной после успешной записи. Это сохраняет предыдущую копию при ошибке.
При занятом файле служба повторяет попытку после паузы.

[Не останавливая службу, извлекаю demo.exe из ZIP и запускаю извлечённую копию.]

Тестовая программа запускается из резервной копии. Окно принадлежит demo.exe;
наша служба выполняла копирование его файла.

[Закрываю тестовую программу и ZIP. В «Службах» выбираю «Перезапустить».
Дожидаюсь новой строки Backup ready, затем останавливаю службу кнопкой оснастки.]

Управление работает через стандартную оснастку Windows. При остановке SCM передаёт
запрос службе, она завершает работу, освобождает ресурсы и сообщает STOPPED.

[Для своей команды снова выполняю start, дожидаюсь готовности и выполняю stop.]

Та же остановка доступна через мой SCP. Закрытие управляющего терминала само по себе
службу не остановит: её процесс запущен SCM отдельно.

[Выполняю .\backup_service.exe remove и обновляю список.]

Регистрация службы удалена. Исполняемый файл, настройки, исходные данные и готовая
резервная копия остаются на диске.

## 4 Вопросы преподавателя

### Что такое UNC

UNC - Universal Naming Convention, формат пути \\сервер\общий_ресурс\папка\файл.
В нашем \\localhost\C$\BSITLab2\source сервером указана сама виртуалка, C$ -
административный общий ресурс C. Знак $ скрывает ресурс из обычного обзора, но не
отменяет права. Служба может не видеть пользовательский сетевой диск Z:, поэтому
используется непосредственный UNC-путь. Доступ нужен учётной записи службы.

### Что такое RPC и где оно здесь

RPC - Remote Procedure Call, удалённый вызов процедур. Клиент передаёт запрос и параметры
другому процессу, там выполняется процедура, результат возвращается клиенту.
RPC организует передачу параметров и результатов. Это возможно на одном компьютере
и между компьютерами. SCM является RPC-сервером. Мы используем готовые функции
Windows для обращения к SCM; самостоятельный RPC-сервер не писали.

### Что такое сервер

Сервер - программа или компонент, который обрабатывает запросы клиентов и предоставляет
услугу. Так также называют компьютер с серверными программами. Клиент отправляет запрос,
сервер его обрабатывает. SCM - сервер управления службами; файловый сервер предоставляет
общие папки. Обычная Windows тоже может предоставлять папку: отдельный физический
компьютер не обязателен. У нас обращение к файлам направлено на саму виртуалку.

Разница: UNC - адрес ресурса, RPC - механизм вызова процедур, сервер - роль участника,
SMB - протокол доступа к общим файлам в нашем примере с C$.

### Что такое команда опрос

Вероятнее всего, SERVICE_CONTROL_INTERROGATE. Это запрос, связанный с текущим состоянием
службы. Он не меняет состояние и не запускает архивацию. Наш обработчик возвращает
NO_ERROR; SCM знает состояние, которое сообщала служба. Опрос состояния службы и
периодическая проверка файлов - разные операции. QueryServiceStatusEx получает состояние из SCM.

### Если поставить маску report*.exe либо report*.xlsx

report*.exe выбирает имена от report до .exe: report.exe, report1.exe, report_final.exe.
Звёздочка допускает ноль символов. myreport.exe и report.txt не подходят.
Для Excel можно задать report*.xlsx или .xls. Запись на старом фото неоднозначна:
если буквально написать .exal, программа ищет именно такое окончание. Пробелы внутри
маски буквальные. Фильтрация проверяет имя, а не фактический формат содержимого.

### Что такое ACP

Если вопрос о кодировках: ACP - ANSI Code Page, текущая ANSI-кодовая страница Windows.
Кодовая страница задаёт интерпретацию байтов текста. Windows-1251 - пример для кириллицы;
ACP не обязана быть 1251 везде. У нас конфигурация UTF-8, Unicode-функции Windows для путей
и UTF-8 для имён ZIP. Если на фото имелось в виду SCP, это программа управления службами.

### Где постоянно встречаем службы Windows

Обновления, печать, звук, сетевые функции. Print Spooler обслуживает очередь печати,
Windows Update - обновления, Windows Audio - звуковую подсистему. Не все службы
постоянно работают и не все запускаются автоматически. У нашей ручной запуск.

### Что такое сигнатура

Нужен контекст. В вопросе о WinAPI-функции обычно имеют в виду ожидаемый интерфейс
вызова: параметры, результат и соглашение о вызове. Windows должна правильно вызвать
обработчик. Сигнатура файла - характерные байты формата, например PE\0\0 в PE-заголовке
Windows EXE. Переименование TXT в EXE не меняет содержимое. Наша маска выбирает по имени.
Электронная подпись - отдельное понятие.

### Что такое SCP и SCM

SCP - Service Control Program, управляющая программа. SCM - Service Control Manager,
системный менеджер Windows. SCP просит, SCM управляет, служба выполняет полезную работу.
install/start/stop/remove - команды SCP, копирование файлов - работа службы.

### Что будет с процессом при остановке службы

Процесс нашей службы штатно завершится после Stop и освобождения ресурсов.
Незавершённый временный ZIP не заменяет готовую копию. Отдельно запущенный demo.exe
продолжит работать: его выполнением служба не управляет. Несколько служб могут
делить один процесс, но у нас выбран собственный процесс.

### Почему нельзя при инициализации

Вопрос на фото оборван; точное продолжение неизвестно. Если речь о Stop: ресурсы
могут быть ещё не созданы. Сначала создаём их, затем разрешаем приём остановки.
В START_PENDING наша служба Stop не принимает.
Если речь о запуске другой службы через StartService во время инициализации:
документация предупреждает о блокировке базы служб SCM и блокирующемся вызове.
Необходимые зависимости описываются в настройках службы. Нужно дослушать точный вопрос.

## 5 Дополнительные вопросы

1. Чем служба отличается от фоновой программы? Интеграцией с SCM, состояниями
   и обработкой управления. Одного отсутствия окна недостаточно.
2. Зачем делать службой? Для фоновой задачи под управлением ОС, независимо от окна
   пользователя. Службы могут запускаться автоматически; у нашей запуск ручной.
3. Что при install? Регистрируются имя, путь к EXE, тип запуска, тип процесса и
   учётная запись. Windows сохраняет параметры в базе служб и реестре.
4. Где запись? HKLM\SYSTEM\CurrentControlSet\Services\BSITLab2Backup.
5. Зачем свой SCP? Требование задания и управление своими командами.
6. Чего нет в оснастке «Службы»? Обычных команд регистрации произвольного EXE
   как новой службы и удаления регистрации. Это делает наш SCP.
7. Start без install? Нет, сначала нужна регистрация. once её не требует.
8. Stop и remove? Stop останавливает, remove удаляет регистрацию.
9. Remove удалит ZIP? Нет, файлы остаются.
10. Закрытие PowerShell остановит службу? Нет, её процесс запущен SCM отдельно.
11. Повторный start? Второй экземпляр не создаётся; проверка идёт в существующем процессе.
12. Зачем backup.ini? Изменение настроек без пересборки. Применение - после перезапуска.
13. Несколько mask? ИЛИ: достаточно совпадения с одной; дубликатов нет.
14. Рекурсия? Обработка папки с повторением той же операции для подпапок.
15. Одинаковые имена конфликтуют? Нет, в ZIP хранится относительный путь.
16. Как находятся изменения? Сравнением имён, размеров и самих байтов с ZIP.
17. Правка той же длины обнаружится? Да, даже с сохранённой датой файла.
18. Изменился исключённый файл? Из-за него архив не обновляется.
19. ZIP переписывается каждые две секунды? Нет, только при различиях.
20. Обновление мгновенное? Нет, пауза плюс время проверки и записи.
21. Почему периодическая проверка? Для небольшого учебного набора это простой
    способ с обычным доступом к файлам и UNC. Цена - чтение выбранных данных.
22. Почему ZIP пересобирается целиком? Это упрощает корректную запись и сохранение
    старой копии при ошибке. Внешний путь прежний, новых имён резервных копий нет.
23. Удалён исходный файл? После обновления он исчезнет из актуального ZIP.
    Это снимок текущего набора, без истории версий.
24. Файл занят? RETRY и повторная попытка; предыдущий ZIP остаётся.
25. ZIP открыт в Проводнике? Чтение возможно. Если просмотрщик мешает замене,
    его нужно закрыть; служба обновит архив сама.
26. Почему нельзя внешний архиватор? Ограничение задания. Используется miniz внутри процесса.
27. Зачем временный файл? Чтобы публиковать только успешно завершённую копию.
28. Файлы целиком в памяти? Нет, чтение и сравнение порциями.
29. Событие остановки? Объект синхронизации Windows; сигнал означает запрос завершения.
30. Дескриптор? Выданное Windows значение для обращения к открытому объекту.
31. Почему обработчик Stop короткий? Он передаёт запрос; основная работа освобождает ресурсы.
32. Запуск после перезагрузки? В нашей настройке ручной.
33. Учётная запись? LocalSystem; доступ проверяется для неё.
34. UNC гарантирует доступ? Нет, нужны доступный ресурс и права службы.
35. Проверен любой удалённый сервер? Нет; localhost относится к виртуалке.
    Для другого сервера проверяют доступность и подходящую учётную запись.
36. Шифрование есть? Нет.
37. Связь с ИБ? Восстановление данных и поддержание доступности.
38. Согласованный снимок всех документов? VSS нет, файлы копируются последовательно;
    последующие изменения попадут в следующую успешную проверку.
39. RUNNING равно «архив готов»? Нет; готовность копии подтверждают свежая строка
    Backup ready/Backup updated и проверенное содержимое ZIP.
