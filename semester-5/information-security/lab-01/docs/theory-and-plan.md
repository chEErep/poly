# Лабораторная работа №1: распределённая система сбора информации

Этот конспект объясняет лабораторную с нуля и одновременно служит планом разработки. Он составлен по двум файлам из папки:

- `БСИТ. Лабораторная 1.pdf` — полное задание и теоретическая часть;
- `Лабораторная_№1_Порядок_демонстрации.pdf` — обязательный порядок демонстрации, который преподаватель называет «50% успеха».

> Важное уточнение: примеры из методички написаны под старые версии Windows. Требования преподавателя сохраняются, но часть API в примерах устарела. Ниже отдельно указано, что требует методичка и какие функции разумно использовать в современной реализации.

---

## 1. Что нужно сделать в одном абзаце

Нужно написать на языке C две Windows-программы:

1. **Агент-сервер** постоянно работает на наблюдаемом компьютере, принимает TCP-подключения, получает формализованные запросы и возвращает сведения о своей системе.
2. **Центральный клиент** подключается к одному или нескольким агентам, выбирает тип запроса, отправляет его и показывает структурированный ответ.

Сервер должен параллельно обслуживать много соединений через **Windows I/O Completion Ports (IOCP)**. Все прикладные сообщения после установки сеансового ключа должны передаваться в зашифрованном виде. Сеансовый симметричный ключ передаётся с защитой асимметричным алгоритмом. Для демонстрации обязательна хотя бы одна виртуальная машина.

## 2. Что именно требует лабораторная

### 2.1. Информация, которую должен уметь возвращать сервер

Для каждого пункта нужен **отдельный тип запроса**:

1. Тип и версия операционной системы.
2. Текущее время.
3. Время, прошедшее с момента запуска ОС (uptime).
4. Информация об используемой памяти.
5. Список подключённых дисков с типом диска и файловой системой:
   - локальный (fixed);
   - сетевой (remote/network);
   - съёмный (removable);
   - при необходимости другие типы: CD/DVD, RAM-диск, неизвестный тип.
6. Свободное место на локальных дисках.
7. Права доступа к указанному:
   - файлу;
   - каталогу;
   - ключу реестра.
8. Владелец указанного файла, каталога или ключа реестра.

Ответ должен быть не просто красивым текстом для человека, а **формализованным сообщением**, которое однозначно разбирается программой.

### 2.2. Требования к серверу

- Windows-консольное приложение без постоянного интерактивного управления пользователем.
- Сервер заранее запускается и ожидает подключения.
- На консоль выводится диагностика:
  - запуск и адрес прослушивания;
  - подключение клиента;
  - отключение клиента;
  - тип полученного запроса;
  - успешный ответ или код ошибки.
- Для сетевого обмена используются обычные WinSock API, а не MFC и не сторонняя обёртка.
- Параллельная обработка запросов выполняется через **IOCP**.

### 2.3. Требования к клиенту

Пользователь должен иметь возможность:

- указать IP-адрес или имя сервера;
- указать порт;
- выбрать тип запроса;
- для запросов прав/владельца указать путь и тип объекта;
- инициировать запрос;
- увидеть ответ или понятную ошибку.

Методичка не требует GUI прямо. Поэтому для первой версии разумно сделать простой консольный клиент с меню. Это легче полностью понять и защитить. GUI можно добавить позже, если преподаватель явно его требует.

### 2.4. Особые требования к выводу ACL и владельца

Для каждой ACE в DACL нужно показать как минимум:

- SID субъекта;
- имя субъекта, если SID удалось разрешить через `LookupAccountSidW`;
- тип ACE: разрешающая, запрещающая и т. д.;
- флаги и область наследования;
- числовую маску доступа;
- номера установленных битов маски;
- названия прав, соответствующие этим битам для данного типа объекта.

Для владельца нужно показать:

- SID;
- имя учётной записи/группы, если оно разрешается.

### 2.5. Требования к шифрованию

- После согласования ключа все прикладные запросы и ответы идут в зашифрованном виде.
- Для основного обмена используется симметричное шифрование с сеансовым ключом.
- Сеансовый ключ создаётся заново для соединения или сеанса.
- Для безопасной передачи сеансового ключа используется асимметричное шифрование.
- В задании прямо указано **CryptoAPI**, то есть семейство функций `Crypt*`.

## 3. Что обязательно показать при сдаче

В файле с порядком демонстрации перечислен минимальный сценарий.

### 3.1. Инфраструктура

- Хотя бы одна виртуальная машина обязательна.
- Нужно запустить один центральный клиент и несколько серверов, в документе названы серверы 1 и 2.
- Машины должны находиться в сети и видеть друг друга по IP.

Практичная схема:

```text
Хостовая Windows                    Виртуальная Windows
-----------------                  -------------------
central_client.exe  ----------->   agent_server.exe (сервер 1)
agent_server.exe    <-----------   соединение по TCP
(сервер 2)
```

Так одной VM достаточно: один сервер работает в VM, второй — на основной машине, а клиент можно запустить на основной машине.

### 3.2. Установка сеансового ключа и Wireshark

Последовательность демонстрации:

1. Запустить Wireshark.
2. Выбрать правильный сетевой интерфейс.
3. Установить capture/display filter по IP-адресам клиента и сервера 1 и, желательно, по TCP-порту программы.
4. Подключить клиента к серверу 1.
5. Показать пакеты обмена публичным ключом и защищённым сеансовым ключом.
6. Запросить тип и версию ОС.
7. Показать, что открытая строка ответа в пакетах не видна: в TCP payload находится шифртекст.

Важно: наличие непонятных байтов в Wireshark ещё не доказывает криптографическую корректность. На защите нужно также объяснить, какой алгоритм выбран, где создаётся ключ, чем он защищён и как стороны понимают границы сообщений.

### 3.3. Права доступа

1. Запросить ACL каталога на сервере 1.
2. Запросить ACL другого каталога на сервере 2.
3. Изменить права тестового каталога на сервере 1 штатными средствами Windows.
4. Повторить запрос.
5. Показать, какие ACE/маски изменились.

Для безопасности лучше заранее создать отдельный тестовый каталог, например `C:\Lab1Demo`, а не менять ACL системных папок.

### 3.4. Диски и флеш-накопитель

1. Запросить список дисков и свободное место.
2. Подключить флеш-накопитель к машине, где работает сервер 1. Для VM может понадобиться USB passthrough.
3. Повторить запрос.
4. Показать новый том, его тип `DRIVE_REMOVABLE`, файловую систему и свободное место.

Здесь формулировки двух документов немного расходятся: полное задание отдельно говорит о типах подключённых дисков и свободном месте на локальных дисках, а сценарий сдачи хочет увидеть флешку в повторном списке. Поэтому в реализации лучше одним запросом возвращать **все доступные тома**, а для каждого указывать тип, файловую систему, общий и свободный объём. Тогда демонстрация однозначна.

## 4. Рекомендуемая архитектура

### 4.1. Кто инициирует передачу

Рекомендуемый вариант: **центральный клиент инициирует соединение и каждый запрос**.

Причины:

- клиент знает, когда и какие сведения ему нужны;
- серверу не нужно знать адрес центральной машины;
- легче управлять несколькими агентами;
- меньше нежелательного исходящего трафика;
- демонстрация совпадает с методичкой: клиент запрашивает, сервер отвечает.

### 4.2. Кто постоянно работает

На наблюдаемых компьютерах постоянно работают агенты-серверы. Центральный клиент запускается оператором или планировщиком, подключается к нужным агентам, собирает данные и завершает соединения.

### 4.3. Stateless или stateful

Полностью stateless TCP-сервер здесь невозможен, потому что для каждого активного соединения нужно хранить:

- состояние рукопожатия;
- сеансовый ключ;
- текущий приём заголовка/тела сообщения;
- незавершённую операцию `WSARecv` или `WSASend`;
- буферы и смещения частично переданных данных.

Поэтому корректная формулировка:

> Сервер хранит **состояние соединения** (stateful transport/session), но обработка прикладных запросов по возможности не зависит от предыдущих запросов. Каждый запрос содержит все необходимые параметры, а сервер не ведёт долговременную пользовательскую сессию.

Это упрощает повтор запросов и обработку ошибок, но позволяет использовать один сеансовый ключ в пределах соединения.

### 4.4. Логические модули

```text
central_client.exe
├── ввод адреса и команды
├── TCP-подключение
├── установка сеансового ключа
├── упаковка/шифрование запроса
├── приём/проверка/расшифрование ответа
└── форматированный вывод

agent_server.exe
├── запуск WinSock и слушающего сокета
├── AcceptEx + IOCP
├── таблица контекстов соединений
├── разбор кадров протокола
├── криптографический контекст соединения
├── диспетчер типов запросов
├── модуль сведений о системе
├── модуль ACL/владельца
└── диагностический журнал
```

## 5. База сетевого обмена

### 5.1. Что такое TCP в этой работе

TCP даёт:

- надёжную доставку байтов;
- сохранение порядка байтов;
- обнаружение разрыва соединения.

TCP **не сохраняет границы сообщений**. Один вызов `send` на 100 байт не обязан соответствовать одному `recv` на 100 байт. Возможны варианты:

- `send(100)` → `recv(40)` + `recv(60)`;
- два `send` могут прийти одним `recv`;
- `send`/`WSASend` может отправить только часть буфера.

Следовательно, программе нужен собственный **framing** — правило определения начала и длины каждого прикладного сообщения.

### 5.2. Жизненный цикл WinSock

Упрощённо сервер выполняет:

1. `WSAStartup`.
2. `WSASocketW` с `WSA_FLAG_OVERLAPPED`.
3. `bind`.
4. `listen`.
5. Асинхронный `AcceptEx`.
6. Связь принятого сокета с IOCP.
7. Асинхронные `WSARecv` и `WSASend`.
8. `shutdown`/`closesocket` при завершении.
9. `WSACleanup` при остановке процесса.

Клиент на первом этапе может быть блокирующим: это не мешает серверу демонстрировать IOCP. Его шаги проще: `WSAStartup` → `getaddrinfo` → `socket/connect` → обмен → `closesocket` → `WSACleanup`.

## 6. Предлагаемый прикладной протокол

### 6.1. Почему нельзя отправлять C-структуру «как есть»

Это частая учебная ошибка. Компилятор может добавить padding, размер типов может отличаться, а порядок байтов на разных архитектурах может быть разным. Поэтому поля сериализуются явно.

### 6.2. Формат кадра

Для понятной реализации предлагается фиксированный заголовок длиной 24 байта:

| Смещение | Размер | Поле | Смысл |
|---:|---:|---|---|
| 0 | 4 | `magic` | константа `BSI1`, позволяет отвергнуть чужой трафик |
| 4 | 1 | `version` | версия протокола, сначала `1` |
| 5 | 1 | `kind` | request, response, handshake, error |
| 6 | 2 | `type` | конкретный тип запроса/ответа |
| 8 | 4 | `request_id` | связывает ответ с запросом |
| 12 | 4 | `flags` | encrypted, more fragments и т. п. |
| 16 | 4 | `payload_len` | число байтов после заголовка |
| 20 | 4 | `reserved` | пока 0; запас для совместимости |

Все многобайтовые числа передаются в **network byte order**. Для 16/32-битных значений используются `htons`, `htonl`, `ntohs`, `ntohl`.

На приёме сначала накапливаются ровно 24 байта заголовка, затем проверяется длина, после чего принимается ровно `payload_len` байт тела.

### 6.3. Ограничения размеров

Длина из сети недоверенная. До выделения памяти нужно проверить:

```text
0 <= payload_len <= MAX_PAYLOAD
```

Для лабораторной разумный предел, например, 1 MiB. Для путей и небольших ответов этого более чем достаточно. При превышении сервер отправляет формальную ошибку и закрывает соединение.

### 6.4. Типы запросов

Пример нумерации:

```text
1  GET_OS
2  GET_TIME
3  GET_UPTIME
4  GET_MEMORY
5  GET_DRIVES
6  GET_DISK_SPACE
7  GET_ACL
8  GET_OWNER
```

Служебные типы рукопожатия должны находиться в отдельном диапазоне, например `0x1001` и выше.

### 6.5. Полезная нагрузка

Для первой понятной версии удобно использовать UTF-8 `key=value` строки внутри кадра:

```text
status=ok
major=10
minor=0
build=26100
name=Windows 11
```

Для списков можно повторять индексированные поля:

```text
count=2
drive.0.root=C:\
drive.0.type=fixed
drive.0.fs=NTFS
drive.0.free_bytes=123456789
drive.1.root=E:\
drive.1.type=removable
drive.1.fs=exFAT
drive.1.free_bytes=987654321
```

Это проще JSON-парсера, но всё ещё формализовано. Правила должны быть строгими:

- одна строка — одно поле;
- разделитель первой пары — `=`;
- текст кодируется UTF-8;
- символы перевода строки и `=` в пользовательских значениях должны экранироваться или кодироваться;
- длина всего payload берётся из заголовка, а не ищется по нулевому байту.

Позже можно перейти на JSON или TLV, но для первой защиты это добавит зависимости и код, который придётся объяснять.

### 6.6. Формат ошибки

Ошибка — нормальный формальный ответ, а не разрыв без объяснения:

```text
status=error
code=5
win32_error=2
message=object_not_found
```

Не нужно отправлять клиенту лишние внутренние данные, адреса памяти и секреты. В консоли сервера диагностика может быть подробнее.

## 7. IO Completion Ports понятным языком

### 7.1. Зачем нужен IOCP

Наивная схема «один клиент — один поток» проста, но плохо масштабируется:

- каждый поток требует стек и ресурсы;
- большое число потоков создаёт переключения контекста;
- большинство потоков часто просто ждут сеть.

IOCP отделяет **запуск операции** от **уведомления о её завершении**:

1. Программа просит ОС принять, получить или отправить данные.
2. Операция может завершиться позже.
3. Пока ОС работает с сетью, рабочий поток может обработать другое соединение.
4. После завершения ОС кладёт пакет завершения в очередь IOCP.
5. Рабочий поток забирает пакет через `GetQueuedCompletionStatus`.

### 7.2. Основные объекты

`CreateIoCompletionPort(INVALID_HANDLE_VALUE, NULL, 0, 0)` создаёт порт завершения.

Повторный вызов `CreateIoCompletionPort((HANDLE)socket, port, key, 0)` связывает сокет с этим портом. `key` позволяет понять, какому соединению относится событие. Безопаснее передавать указатель на живой контекст соединения или устойчивый ID, но жизненный цикл этого объекта должен быть строго контролируемым.

`OVERLAPPED` описывает конкретную незавершённую операцию. Обычно создают расширенную структуру:

```c
typedef enum io_operation {
    IO_ACCEPT,
    IO_RECV,
    IO_SEND
} io_operation;

typedef struct io_context {
    OVERLAPPED overlapped;
    WSABUF buffer;
    io_operation operation;
    size_t offset;
} io_context;
```

Так по адресу `OVERLAPPED`, вернувшемуся из очереди, можно определить тип завершённой операции.

### 7.3. Почему буфер нельзя освобождать сразу

При `WSARecv`/`WSASend` с `OVERLAPPED` ОС может продолжать пользоваться:

- структурой `OVERLAPPED`;
- `WSABUF`;
- памятью, на которую указывает `WSABUF.buf`.

Все эти объекты должны жить до получения соответствующего пакета завершения. Даже после запроса отмены операции нужно дождаться завершения/отмены. Иначе возникает use-after-free и повреждение памяти.

### 7.4. Возврат `WSA_IO_PENDING` — не ошибка работы программы

Асинхронная функция может вернуть `SOCKET_ERROR`, а `WSAGetLastError()` — `WSA_IO_PENDING`. Это означает: операция успешно поставлена в очередь и завершится позже.

Реальной ошибкой является другой код. Каждый такой код нужно логировать и корректно закрывать контекст соединения.

### 7.5. Частичные операции

Завершение `WSASend` не гарантирует, что отправлен весь кадр. Нужно хранить `offset`:

```text
отправлено += bytes_transferred
если отправлено < total:
    запустить WSASend для оставшейся части
иначе:
    перейти к следующему состоянию
```

То же относится к приёму заголовка и payload.

### 7.6. Разрыв соединения

Для операции чтения `bytes_transferred == 0` обычно означает корректное закрытие соединения удалённой стороной. Нужно:

1. пометить соединение закрывающимся;
2. отменить оставшиеся операции через `CancelIoEx`, если это необходимо;
3. не освобождать контекст, пока все pending operation не дали завершение;
4. закрыть сокет;
5. уничтожить ключи и обнулить секретные буферы.

Пример методички использует `CancelIo`, но для явной отмены конкретных overlapped-операций современная реализация обычно использует `CancelIoEx`.

### 7.7. Рабочие потоки

Несколько worker threads вызывают `GetQueuedCompletionStatus`. Значение concurrency у IOCP ограничивает число одновременно выполняющихся потоков, а не число соединений. Начальная простая настройка — число логических процессоров или значение 0 при создании порта, позволяющее системе выбрать concurrency.

Для лабораторной не нужно создавать сотни потоков: преимущество IOCP как раз в обслуживании множества соединений небольшим пулом.

## 8. Установка сеансового ключа и шифрование

### 8.1. Зачем два вида криптографии

**Асимметричное шифрование** удобно для обмена секретом: публичный ключ можно передать открыто, а расшифровать защищённые им данные может владелец приватного ключа. Но оно медленное и имеет ограничение размера сообщения.

**Симметричное шифрование** быстро и подходит для всех запросов/ответов, но обе стороны должны заранее получить один секретный ключ.

Поэтому используется гибридная схема:

```text
клиент: создаёт RSA public/private key pair
клиент -> сервер: public key
сервер: генерирует случайный AES session key
сервер -> клиент: AES key, зашифрованный RSA public key клиента
клиент: расшифровывает AES key своим private key
обе стороны: используют AES для прикладных сообщений
```

### 8.2. Реализация именно через CryptoAPI

Если следовать формулировке задания буквально, подходят:

- `CryptAcquireContextW` — получить контекст CSP;
- `CryptGenKey` — создать RSA key exchange pair и сеансовый ключ;
- `CryptExportKey` — экспортировать `PUBLICKEYBLOB` или защищённый `SIMPLEBLOB`;
- `CryptImportKey` — импортировать публичный/сеансовый ключ;
- `CryptEncrypt` и `CryptDecrypt` — шифровать сообщения;
- `CryptDestroyKey` — уничтожать ключи;
- `CryptReleaseContext` — освобождать контекст.

Для поддержки AES нужен подходящий provider type, обычно `PROV_RSA_AES`. Нельзя выбирать DES, 3DES или RC4 только потому, что они встречаются в старых примерах.

### 8.3. Почему CryptoAPI — legacy

Microsoft считает классический CryptoAPI устаревшим и рекомендует CNG (`BCrypt*`/`NCrypt*`) для нового ПО. Но учебная работа прямо требует CryptoAPI, поэтому разумная позиция на защите:

> В лабораторной используется CryptoAPI для соответствия заданию. В реальном новом проекте предпочтительнее CNG или готовый TLS через Schannel. Алгоритмы при этом выбираются современные: AES и RSA достаточной длины, а не RC4/DES.

### 8.4. IV, конфиденциальность и целостность

Одного «AES» недостаточно. Нужно определить режим и IV.

- ECB использовать нельзя: одинаковые блоки открытого текста дают одинаковые блоки шифртекста.
- Для CBC каждому независимому сообщению нужен новый случайный IV.
- IV не является секретом и передаётся вместе с шифртекстом.
- Повтор IV с тем же ключом недопустим.

Критически важный момент: **шифрование без аутентификации не защищает от изменения пакетов**. CBC скрывает содержимое, но активный атакующий может модифицировать шифртекст. В полноценном решении нужен MAC (например HMAC-SHA-256 по заголовку, IV и ciphertext) с отдельным ключом либо authenticated encryption, например AES-GCM в CNG.

Если преподаватель требует строго только CryptoAPI и минимальную схему из методички, реализацию целостности нужно согласовать отдельно. В конспекте это не замалчивается: confidentiality и integrity — разные свойства.

### 8.5. Защита от replay

Поле `request_id` помогает связывать запрос и ответ, но само по себе не останавливает повтор старого пакета. Для защиты от replay в криптографически защищаемые данные включают:

- идентификатор соединения/сеанса;
- монотонный sequence number;
- тип сообщения;
- длину;
- направление обмена.

Получатель отклоняет уже использованный или неожиданный sequence number.

### 8.6. Ограничение схемы из методички

Если клиент просто присылает публичный ключ без аутентификации, возможна атака man-in-the-middle: посредник заменит ключ своим. Шифрование трафика в Wireshark будет видно, но подлинность стороны не доказана.

Для реальной системы нужны сертификаты/закреплённые публичные ключи или TLS. Для лабораторной можно реализовать требуемый учебный обмен и честно назвать его ограничение.

## 9. Получение системной информации в современной Windows

### 9.1. Тип и версия ОС

В методичке показан `GetVersionEx`, однако начиная с Windows 8.1 его результат зависит от application manifest, а API помечен устаревшим.

Варианты:

1. **Для строгого соответствия методичке:** `GetVersionExW` + корректный manifest с supported OS GUID.
2. **Для получения фактического build number:** динамический вызов `RtlGetVersion` из `ntdll.dll`; это низкоуровневый подход, который нужно изолировать в одной функции и тщательно проверять.
3. Для проверки доступности конкретной возможности лучше проверять саму возможность, а не номер Windows.

В ответе полезно возвращать `major`, `minor`, `build` и понятное имя, но имя не должно вычисляться по старой таблице, которая заканчивается Windows 8.1.

### 9.2. Текущее время

- `GetSystemTime` возвращает UTC.
- `GetLocalTime` возвращает локальное время машины сервера.

Чтобы ответ был однозначен, лучше вернуть UTC в ISO 8601 и отдельно timezone offset, например:

```text
utc=2026-09-20T13:25:40Z
local=2026-09-20T16:25:40+03:00
unix_seconds=1789910740
```

Методичка требует выводить время в секундах, минутах, часах, днях и т. д. Для текущего времени это двусмысленно; на практике формат даты/времени и Unix timestamp закрывают обе потребности, а uptime форматируется отдельно.

### 9.3. Uptime

Нужно использовать `GetTickCount64`, который возвращает миллисекунды с момента запуска системы в 64-битном значении.

Старый `GetTickCount` имеет 32-битное переполнение примерно через 49,7 суток. Для современного кода он не подходит.

Преобразование:

```text
total_seconds = milliseconds / 1000
days    = total_seconds / 86400
hours   = (total_seconds % 86400) / 3600
minutes = (total_seconds % 3600) / 60
seconds = total_seconds % 60
```

Передавать лучше и исходное `total_milliseconds`, и разложенные компоненты.

### 9.4. Память

Вместо старой `GlobalMemoryStatus` используется `GlobalMemoryStatusEx` со структурой `MEMORYSTATUSEX`.

Перед вызовом обязательно:

```c
MEMORYSTATUSEX state;
ZeroMemory(&state, sizeof(state));
state.dwLength = sizeof(state);
```

Полезные поля:

- `dwMemoryLoad` — приблизительная загрузка памяти в процентах;
- `ullTotalPhys` — физическая память всего;
- `ullAvailPhys` — доступная физическая память;
- `ullTotalPageFile`, `ullAvailPageFile`;
- `ullTotalVirtual`, `ullAvailVirtual`.

Все размеры 64-битные; нельзя складывать их в `DWORD` или `unsigned int`.

### 9.5. Диски и файловая система

Рекомендуемая последовательность:

1. `GetLogicalDriveStringsW` — получить корни томов вида `C:\`.
2. `GetDriveTypeW` — определить тип.
3. `GetVolumeInformationW` — получить файловую систему и метку тома.
4. `GetDiskFreeSpaceExW` — получить общий и свободный объём.

`GetDiskFreeSpaceExW` возвращает `ULARGE_INTEGER`; нельзя обрезать до 32 бит.

Нужно нормально обрабатывать ситуации:

- пустой CD-привод;
- отключившийся сетевой диск;
- отсутствие доступа;
- флешка была удалена между двумя вызовами;
- файловая система не распознана.

### 9.6. Почему используем `W`-версии функций

Windows внутренне работает с UTF-16. `GetNamedSecurityInfoW`, `LookupAccountSidW`, `GetVolumeInformationW` и другие wide API корректно обрабатывают русские имена и пути.

На границе сетевого протокола можно использовать UTF-8:

```text
UTF-8 из сети -> MultiByteToWideChar -> UTF-16 для WinAPI
UTF-16 от WinAPI -> WideCharToMultiByte -> UTF-8 в ответ
```

Результаты обоих преобразований и размеры буферов нужно проверять.

## 10. Права доступа Windows

### 10.1. Security descriptor

Защищаемый объект Windows имеет security descriptor. В нём могут находиться:

- SID владельца;
- SID основной группы;
- DACL — кто что может/не может делать;
- SACL — какие обращения нужно аудитировать;
- control flags.

### 10.2. SID

SID — уникальный идентификатор субъекта безопасности: пользователя, группы или системной сущности. Имя можно переименовать, а SID остаётся тем идентификатором, по которому Windows связывает права с субъектом.

Для вывода:

- `ConvertSidToStringSidW` превращает бинарный SID в строку вида `S-1-5-...`;
- `LookupAccountSidW` пытается получить домен и имя;
- ошибка разрешения имени не отменяет сам SID — строковый SID всё равно должен быть показан.

### 10.3. DACL, ACL и ACE

- ACL — упорядоченный список ACE.
- DACL определяет разрешение/запрет доступа.
- ACE относится к конкретному SID, содержит тип, маску прав и флаги наследования.

Порядок ACE важен. Обычно явные deny-ACE идут перед allow-ACE, а явно заданные ACE — перед унаследованными.

Особо важно различать:

- **NULL DACL** — ограничений нет, полный доступ всем; это опасное состояние;
- **пустая DACL** — ACE нет, доступ никому не предоставлен.

### 10.4. Получение DACL

Для файла/каталога:

```c
GetNamedSecurityInfoW(
    path,
    SE_FILE_OBJECT,
    DACL_SECURITY_INFORMATION,
    NULL,
    NULL,
    &dacl,
    NULL,
    &security_descriptor
);
```

Для реестра применяется `SE_REGISTRY_KEY`, но формат имени ключа и необходимые права отличаются. Этот обработчик лучше делать отдельно, а не пытаться подставить строку реестра в файловую функцию.

После использования `security_descriptor` освобождается через `LocalFree`.

### 10.5. Разбор ACE

1. Проверить, присутствует ли DACL и не является ли она NULL.
2. Получить число ACE через `GetAclInformation`.
3. Для каждого индекса вызвать `GetAce`.
4. Проверить `AceType` до приведения указателя к конкретной структуре.
5. Извлечь SID и убедиться через `IsValidSid`, что он корректен.
6. Вывести тип, SID, имя, маску и флаги.

Нельзя считать, что каждая запись — `ACCESS_ALLOWED_ACE`: существуют deny, audit, object-specific и другие виды ACE.

### 10.6. Маска доступа

Access mask — битовое поле. Один установленный бит означает конкретное право. Есть:

- standard rights: `DELETE`, `READ_CONTROL`, `WRITE_DAC`, `WRITE_OWNER`, `SYNCHRONIZE`;
- generic rights: `GENERIC_READ`, `GENERIC_WRITE`, `GENERIC_EXECUTE`, `GENERIC_ALL`;
- object-specific rights: для файлов и каталогов это, например, чтение данных, запись данных, добавление файла, перечисление каталога и т. д.

Generic mask при необходимости переводится в конкретные права функцией `MapGenericMask` с правильным `GENERIC_MAPPING` для типа объекта.

### 10.7. Наследование

Флаги ACE показывают, передаётся ли право дочерним объектам:

- `OBJECT_INHERIT_ACE` — наследование файлами/дочерними объектами;
- `CONTAINER_INHERIT_ACE` — наследование дочерними контейнерами;
- `INHERIT_ONLY_ACE` — ACE применяется только через наследование;
- `NO_PROPAGATE_INHERIT_ACE` — ограничить дальнейшее распространение;
- `INHERITED_ACE` — ACE уже унаследована.

### 10.8. Владелец

`GetNamedSecurityInfoW` вызывается с `OWNER_SECURITY_INFORMATION`, после чего SID владельца выводится строкой и разрешается в имя.

Владелец и DACL — разные понятия. Владелец обычно имеет возможность изменить DACL, но список разрешённых операций находится именно в DACL.

## 11. Threat model и безопасность реализации

### 11.1. Что защищаем

Assets:

- сведения о конфигурации машины;
- ACL и владельцы объектов;
- пути к файлам и ключам реестра;
- сеансовые ключи;
- доступность агента.

### 11.2. Возможные атакующие

- пассивный наблюдатель сети;
- активный атакующий в сети, способный менять пакеты;
- неавторизованный клиент, который нашёл порт сервера;
- клиент, отправляющий повреждённые длины и команды;
- локальный пользователь с доступом к процессу агента.

### 11.3. Attack surface

- TCP listener;
- parser заголовка и payload;
- криптографическое рукопожатие;
- преобразование UTF-8/UTF-16;
- обработка путей;
- WinAPI для ACL/реестра;
- логирование недоверенных строк;
- очистка контекстов при конкурентных событиях IOCP.

### 11.4. Основные меры

- жёсткий `MAX_PAYLOAD`;
- проверка каждого возвращаемого значения WinAPI;
- 64-битные размеры для памяти/дисков;
- отсутствие `strcpy`, `sprintf` и неконтролируемого форматирования;
- `snprintf`/`StringCchPrintfW` с проверкой;
- отдельное хранение длины — не доверять завершающему `\0` из сети;
- запрет path traversal не решается простой проверкой `..`; если сервер должен работать только с тестовым корнем, нужно канонизировать путь и проверить, что итоговый объект остаётся внутри разрешённого каталога;
- сервер запускается без прав администратора, если повышенные права не нужны;
- секреты очищаются `SecureZeroMemory` перед освобождением;
- ключи уничтожаются на всех путях выхода;
- `request_id` и sequence number проверяются;
- ошибки наружу не раскрывают внутренние адреса и секреты.

### 11.5. Авторизация запросов

Шифрование не означает авторизацию. Любой клиент, способный выполнить неаутентифицированное рукопожатие, может запросить сведения.

Для полноценного продукта нужны:

- проверка сертификата или заранее закреплённого ключа;
- список разрешённых клиентов;
- журналирование;
- ограничение доступных путей/ключей реестра;
- rate limiting.

Методичка этого прямо не требует, но на защите полезно объяснить разницу:

- encryption защищает confidentiality;
- MAC/signature защищает integrity/authenticity сообщения;
- authentication устанавливает личность стороны;
- authorization решает, что этой стороне разрешено.

## 12. Обработка ошибок

Нельзя писать только «что-то не работает». Ошибка должна быть привязана к уровню:

1. **WinSock:** код `WSAGetLastError`.
2. **Win32:** код `GetLastError` или возвращаемый `DWORD` (например, у security API).
3. **CryptoAPI:** `GetLastError`.
4. **Протокол:** собственный код `BAD_MAGIC`, `BAD_VERSION`, `TOO_LARGE`, `UNKNOWN_REQUEST`, `BAD_ENCODING`.
5. **Прикладной уровень:** `OBJECT_NOT_FOUND`, `ACCESS_DENIED`, `UNSUPPORTED_OBJECT_TYPE`.

Сервер логирует числовой код и контекст операции. Клиент получает безопасный формализованный код и короткое сообщение.

Ресурсы освобождаются централизованно и в обратном порядке создания. Для C удобен один `cleanup:` блок с проверками дескрипторов.

## 13. Поэтапный план разработки

### Этап 0. Архитектура и протокол

Результат:

- схема клиент/агенты;
- таблица типов сообщений;
- формат 24-байтного заголовка;
- лимиты;
- выбранный порт;
- документированный state machine.

Это уже можно показать преподавателю как обоснованный проект, но лучше принести работающий код следующего этапа.

### Этап 1. Первый демонстрационный прототип

Рекомендуемый объём на ближайшие два дня:

- проект на чистом C и CMake;
- IOCP-сервер;
- простой блокирующий консольный клиент;
- формальный framed protocol;
- запросы `GET_TIME`, `GET_UPTIME`, `GET_MEMORY`, `GET_OS`;
- диагностические сообщения сервера;
- проверка нескольких одновременных клиентских запусков;
- запуск клиента и сервера на разных машинах/VM.

На этом этапе шифрование и ACL можно честно обозначить как следующие части. Это не готовая лабораторная, но уже демонстрирует самую архитектурно важную основу: собственный протокол, сеть и IOCP.

### Этап 2. Диски

- `GET_DRIVES`;
- типы дисков;
- файловая система;
- общий/свободный объём;
- тест подключения/отключения флешки.

### Этап 3. ACL и владелец

- сначала файл/каталог;
- затем отдельная ветка для ключа реестра;
- полный вывод SID, имени, ACE type, flags, mask bits и names;
- тестовое изменение ACL.

### Этап 4. CryptoAPI handshake

- публичный RSA key клиента;
- AES session key сервера;
- защищённый экспорт ключа;
- шифрование payload;
- случайный IV;
- sequence number;
- по возможности HMAC;
- проверка в Wireshark.

### Этап 5. Полная демонстрация и hardening

- клиент + сервер 1 + сервер 2;
- VM;
- несколько одновременных соединений;
- некорректные длины и неизвестные команды;
- разрыв клиента во время отправки;
- ошибки доступа;
- повторное подключение;
- cleanup без утечек;
- сценарий сдачи от начала до конца.

## 15. Что нужно уметь объяснить преподавателю

1. Почему агент — сервер, а центральная программа — клиент.
2. Почему клиент инициирует запрос.
3. Какие состояния сервер всё равно хранит, даже если запросы независимы.
4. Почему TCP не является протоколом сообщений.
5. Зачем в заголовке `payload_len` и `request_id`.
6. Почему длину из сети нельзя сразу использовать для `malloc`.

## 16. Ответы на контрольные вопросы

### 16.1. Какова структура списков контроля доступа в Windows?

Защищаемый объект имеет security descriptor. В нём находятся SID владельца/группы, DACL, SACL и управляющие флаги. ACL состоит из упорядоченных ACE. Каждая ACE указывает SID субъекта, тип записи, access mask и флаги наследования. DACL управляет разрешением/запретом доступа, SACL — аудитом обращений.

### 16.2. Что такое наследование прав доступа?

Это механизм автоматического переноса применимых ACE родительского контейнера на дочерние файлы и каталоги. Поведение определяется флагами ACE. Унаследованные записи помечаются `INHERITED_ACE`; явные права обычно имеют приоритет в canonical order.

### 16.3. Для чего используются well-known SID?

Это заранее определённые SID для общеизвестных субъектов, например Everyone, Local System, Administrators. Они позволяют ссылаться на системные группы/сущности независимо от локализованного имени Windows.

### 16.4. Как выглядит схема с сеансовым ключом?

Клиент создаёт асимметричную пару, передаёт публичный ключ. Сервер создаёт случайный симметричный ключ, шифрует его публичным ключом клиента и отправляет. Клиент расшифровывает своим приватным ключом. После этого обе стороны используют симметричный ключ для основного трафика.

### 16.5. Каковы преимущества сеансового ключа?

- Симметричное шифрование быстрее асимметричного.
- Можно шифровать сообщения произвольного размера.
- Компрометация одного сеанса не обязана раскрывать другие, если ключи независимы и долговременные секреты защищены.
- Ключ можно уничтожить после соединения.
- Асимметричный алгоритм используется только для небольшой операции обмена ключом.

## 19. Решение для первого показа

Наиболее полезная часть, которую стоит принести через два дня:

> Работающий IOCP-сервер на чистом C, простой консольный клиент и четыре запроса (`GET_OS`, `GET_TIME`, `GET_UPTIME`, `GET_MEMORY`) через собственный length-prefixed protocol. Запустить сервер на хосте и VM и показать несколько подключений. Отдельно принести таблицу будущих типов запросов и схему key exchange.

Почему этот вариант:

- это уже настоящая часть итоговой архитектуры, а не выбрасываемый макет;
- IOCP — одна из главных целей лабораторной;
- системные функции просты и дают наглядный результат;
- код можно разделить на короткие функции и полностью разобрать;
- поверх готового framing позже добавятся диски, ACL и шифрование без переписывания всей сети.

До реализации нужно подтвердить среду сборки, доступную виртуальную машину и то, согласен ли преподаватель увидеть сначала IOCP/протокол без готового шифрования.
