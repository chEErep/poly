## 1. Что мы вообще сделали

Это распределённая система сбора информации: одна программа спрашивает, другая получает сведения от Windows и отвечает

- Клиент — `lab_client.exe`, программа с меню. Ты выбираешь адрес сервера и запрос
- Сервер — `lab_server.exe`, агент на машине, о которой нужно узнать информацию. Он постоянно ждёт подключения и не требует выбора пунктов меню
- Данные идут через TCP-сокеты WinSock
- Сервер обслуживает принятые соединения через IOCP и несколько рабочих потоков
- После обмена ключами запросы и ответы шифруются средствами CryptoAPI

Важное следствие: если клиент работает на твоём ноутбуке, а подключён к серверу в VM, сведения относятся к VM. Путь `C:\Windows` тоже относится к VM, а не к ноутбуку

Схема нашей демонстрации:

```text
Основная Windows                         VirtualBox: гостевая Windows
192.168.56.1                             192.168.56.101
клиент A ---------------- TCP ---------- сервер 1:27015
клиент B ---------------- TCP ---------- сервер 1:27015
клиент C ---- 127.0.0.1:27015 ---------- сервер 2 на основной Windows
```

IP могут измениться: перед сдачей проверь их. Один процесс клиента подключается к одному серверу; несколько окон клиента — несколько независимых процессов

Сервер 1 и сервер 2 могут использовать одинаковый порт, потому что находятся на разных машинах. Два сервера на одной машине должны использовать разные порты

Архитектура по вопросам методички:

- Инициатор TCP-подключения и запроса — клиент
- Постоянно готов принимать запросы сервер
- Сервер stateful: хранит состояние TCP-соединения, ключ, буферы и этап обмена каждого клиента
- В одном соединении можно выполнить много запросов; повторное подключение на каждый пункт меню не нужно
- Получение сведений выполняется автоматически сервером, но запрос инициируется оператором в меню. Периодического автоматического опроса списка машин в этой версии нет

Почему так: постоянный агент не заставляет оператора запускать команды Windows на каждой машине, а постоянное соединение позволяет повторно использовать уже согласованный AES-ключ

Проверь себя: на какой машине проверяется путь, кто начинает подключение, почему сервер stateful?

Код следует требованиям и схеме обмена ключами, но не является буквальной копией фрагментов методички:

| Методичка / требование | Что в нашем коде | Что говорить честно |
| --- | --- | --- |
| Получить версию ОС через GetVersionEx | Динамический RtlGetVersion, расширенная структура версии | Не используем устаревший пример буквально; читаем major/minor/build и тип продукта |
| Время работы ОС | GetTickCount64 | 64-битное значение миллисекунд, не 32-битный счётчик с коротким периодом переполнения |
| Информация о памяти | GlobalMemoryStatusEx | Расширенная структура с 64-битными объёмами |
| IOCP | WSARecv, WSASend, CreateIoCompletionPort, GetQueuedCompletionStatus | Реальное асинхронное чтение и отправка принятых соединений |
| Пример AcceptEx | Обычный accept в главном потоке | AcceptEx не реализован; не заявлять обратное |
| ACL и владелец | GetNamedSecurityInfo, SID, ACE, маски и флаги | Полностью разбираются обычные allow/deny ACE, иные типы помечаются unsupported |
| Обмен сеансовым ключом | Клиент RSA, сервер AES, RSA-упаковка AES | Роли соответствуют схеме на странице 13 |
| Шифрование данных | Внутренний заголовок и тело зашифрованы AES; внешний заголовок и IV открыты | Не говорить «зашифрован буквально каждый байт TCP» |
| Несколько серверов | Несколько процессов клиента на центральной машине | Единого интерфейса с одновременными соединениями ко всем серверам нет |
| Windows 7/8/10 | API выбраны с расчётом на Windows 7+, фактические запуски на Windows 10/11 | Совместимость с Windows 7/8 не подтверждена запуском |

Если преподаватель требует именно AcceptEx, один процесс клиента на несколько серверов, полный разбор всех вариантов ACE или периодический опрос, это отдельные функциональные доработки, а не косметическая правка. Их нельзя объявлять выполненными. В явных требованиях к серверу обязательны IOCP, а AcceptEx показан в примере

Флешки сейчас нет: поддержка removable в коде есть, но физическое подключение и появление накопителя ещё не продемонстрированы. Лучший вариант — одолжить флешку; альтернативу согласовать с преподавателем. Новый виртуальный fixed-диск не надо называть проверкой USB-флешки

## 4. Минимум языка C, который действительно нужен для этого кода

### 4.1. Функции и их происхождение

Функция — именованный кусок программы, который можно вызвать с параметрами и получить результат. Вызов не означает, что «функция взялась из воздуха»

Есть три группы:

- Наши функции: `build_memory`, `perform_request`, `post_receive`, `lab_crypto_open`. Их реализация написана в проекте; поиск имени приводит в соответствующий `.c`
- Стандартная библиотека C: `printf`, `strlen`, `memcpy`, `fgets`, `malloc/calloc`, `free`. Объявления даёт, например, `<stdio.h>` или `<string.h>`
- Windows/WinSock/CryptoAPI: `GlobalMemoryStatusEx`, `WSARecv`, `CryptEncrypt`. Их реализацию предоставляет Windows; заголовки сообщают компилятору сигнатуры, библиотеки нужны линкеру

`#include` не запускает функцию. Он подключает объявления и определения для компиляции

Пример сигнатуры:

```c
static int build_memory(char *output, size_t output_size)
```

Читать так: функция внутри этого `.c`, возвращает `int`, принимает адрес буфера символов и его размер. Через `output` записывает текст. Возвращаемое `1` означает «текст сформирован», `0` — «сформировать не удалось». Это контракт нашей функции, а не правило для всех Windows API

У `GetNamedSecurityInfo` успех — `ERROR_SUCCESS`, то есть 0. У `GlobalMemoryStatusEx` успех — ненулевой BOOL. У `recv` положительное число — полученные байты, 0 — закрытие соединения, SOCKET_ERROR — ошибка. Нельзя механически считать любое 0 одним и тем же

### 4.2. Указатели, структуры и буферы

`char output[100]` — массив из 100 байтов. `char *output` — указатель, то есть адрес данных; сам указатель не сообщает размер доступного массива. Поэтому вместе с буфером передаётся `output_size`

`&memory` — адрес структуры memory. Windows пишет результаты в эту структуру по адресу. `*used` — значение по адресу used. `client->socket` — поле структуры, на которую указывает client. Для обычной переменной-структуры используется точка: `memory.dwLength`

`sizeof(memory)` — число байтов структуры. `sizeof(pointer)` — размер указателя, а не массива за ним. `strlen(text)` — длина C-строки до нулевого байта; для произвольного шифротекста strlen применять нельзя

`\0` — конец C-строки. `\n` — перевод строки. В исходнике `"C:\\Windows"` содержит один обратный слеш, потому что внутри литерала C слеш экранируется. В меню вводишь `C:\Windows`, без удвоения

`memcpy` копирует байты, когда диапазоны не перекрываются; `memmove` допускает перекрытие. В шифровании это важно: вход и выход могут находиться в одном send_buffer

`calloc` выделяет память и заполняет нулями; `free` освобождает её. Нельзя пользоваться памятью после free. `LocalFree` освобождает определённые буферы Windows, например security descriptor; не надо заменять его на free

`HANDLE`, `HCRYPTKEY`, `SOCKET` — идентификаторы системных ресурсов, а не сам ключ или сам компьютер. `CryptDestroyKey`, `CloseHandle`, `closesocket` освобождают соответствующие ресурсы

### 4.3. Условия и биты

`&&` — логическое «и», `||` — «или», `!` — отрицание. `&` между числами — побитовое И, не то же, что &&. `|` — побитовое ИЛИ. `1u << bit` включает один бит с нужным номером

Например, маска `0x00100020` содержит биты 5 и 20:

```text
1 << 5  = 0x00000020
1 << 20 = 0x00100000
ИЛИ     = 0x00100020
```

Проверка `(mask & ((DWORD)1u << bit)) != 0` спрашивает: включён ли именно этот бит? Цикл проверяет номера от 0 до 31. Для папки бит 5 — FILE_TRAVERSE, бит 20 — SYNCHRONIZE. Для файла бит 5 имеет другое имя: FILE_EXECUTE

`static` у функции ограничивает её видимость одним `.c`; `const` у указателя на данные запрещает менять данные через этот указатель; `typedef` даёт типу удобное имя; `enum` задаёт именованные числовые значения

## 6. Наш протокол: что значит «отправить пакет»

TCP доставляет упорядоченный поток байтов. Наш протокол BSI1 задаёт границы сообщений внутри потока. TCP-сегмент в Wireshark и сообщение BSI1 — разные вещи: сообщение может разбиться на несколько сегментов, несколько сообщений могут попасть в один сегмент

Фиксированный заголовок — 24 байта:

| Смещение | Размер | Поле | Зачем |
| --- | --- | --- | --- |
| 0 | 4 | BSI1 | Признак нашего протокола, magic |
| 4 | 1 | version | Версия протокола, сейчас 1 |
| 5 | 1 | kind | 1=request, 2=response, 3=error |
| 6 | 2 | type | Номер вида запроса/служебного кадра |
| 8 | 4 | request_id | Связать ответ с конкретным запросом |
| 12 | 4 | flags | Сейчас 0 |
| 16 | 4 | payload_len | Сколько байтов прочитать после заголовка |
| 20 | 4 | reserved | Сейчас 0, зарезервировано |

Многобайтные числа записываются big-endian, старшим байтом вперёд. Например, 27015 как 16-битное число — `69 87`, а тип 101 — `00 65`. Порт TCP не является полем нашего BSI1-заголовка

Почему не отправляем память `struct lab_header` целиком: представление struct зависит от padding, ABI и порядка байтов процессора. `lab_encode_header` явно записывает 24 байта; `lab_decode_header` читает их в поля. Сам decode проверяет только magic, остальные условия проверяют вызывающие функции

Типы 1–8 соответствуют меню. Тип 100 — KEY_EXCHANGE. Тип 101 — SECURE_FRAME

После установления ключа формат такой:

```text
Открытый внешний заголовок BSI1, type=101
IV, 16 байт, открытый
AES-шифротекст [внутренний BSI1-заголовок type=1..8 + тело]
```

Внешний заголовок раскрывает version, kind, type=101, request_id и длину. Внутренний заголовок скрывает конкретный запрос и длину его исходного тела. Не надо говорить, что снаружи видна только длина: ID и другие поля тоже видны

Для 1–6 тело внутреннего запроса пустое. Для 7–8 оно содержит путь без завершающего нулевого байта; длина отдельно указана в payload_len. Ответ содержит строки `ключ=значение\n`. `status=error` тоже отправляется внутри шифрованного ответа, а не в открытом виде

Ограничения: payload до 64 КиБ; путь меньше 512 байт в серверном буфере. Эти числа нужны, чтобы не выделять/читать произвольный объём памяти по недоверенному заголовку

Когда преподаватель говорит «отправь запрос ОС», обычно это означает выбрать `1` в нашем клиенте. Wireshark только наблюдает, он не заменяет клиент. Telnet и произвольная строка не выполнят RSA/AES-протокол. Если он просит именно показать байты, открой захват и объясни внешний заголовок, типы 100/101 и длины. Если требуется нестандартный или повреждённый пакет, уточни ожидаемый формат; это отдельное испытание, не пункт меню

## 7. Один запрос от твоей клавиши до результата

Возьмём `GET_MEMORY`, пункт 4. Сначала соединение уже установлено и AES-ключ согласован

1. `client.c:main` читает строку через fgets, преобразует число через strtol, проверяет диапазон 1–8
2. Вызывает `perform_request(socket, &crypto, 4, request_id++, NULL)`. NULL означает, что пути нет. request_id растёт после запроса
3. `perform_request` формирует inner_request: type=4, kind=request, payload_len=0
4. `lab_encode_header` превращает поля в 24 байта
5. `lab_crypto_encrypt_message` создаёт IV и шифрует внутренние 24 байта. Добавляется padding: получаем 32 байта ciphertext плюс 16 байт IV, итого 48 байт
6. Клиент добавляет внешний заголовок type=101, payload_len=48 и отправляет через send_all
7. Сервер ранее запустил WSARecv. IOCP сообщает worker_thread о завершении чтения и числе байтов
8. `complete_receive` сначала собирает ровно 24 байта внешнего заголовка, проверяет ограничения и затем собирает указанное тело
9. `prepare_response` по type=101 вызывает `prepare_secure_response`
10. Сервер расшифровывает тело, проверяет внутренний заголовок и совпадение ID, затем вызывает `lab_build_system_response(4, ...)`
11. Диспетчер в system_info.c выбирает `build_memory`
12. `build_memory` задаёт memory.dwLength и вызывает `GlobalMemoryStatusEx(&memory)`. Windows записывает текущие значения памяти
13. `append_text` собирает текст ответа с проверкой размера буфера
14. Сервер формирует внутренний ответ с type=4 и тем же ID, шифрует его, добавляет внешний заголовок type=101
15. `post_send` запускает WSASend из постоянного send_buffer. `complete_send` при необходимости отправляет остаток, затем снова запускает чтение следующего запроса
16. Клиент через receive_all читает внешний заголовок и тело, расшифровывает, проверяет внутренний заголовок и печатает ровно payload_len байтов через fwrite

Это главная цепочка, которую нужно уметь показать в коде. Не пытайся назвать все параметры Windows API сразу: сначала объясни, кто что делает и почему следующий шаг необходим

Для ACL меняется только внутренний type=8 и появляется путь. Вызов диспетчера выбирает build_acl вместо build_memory. Сокеты, шифрование и IOCP работают по той же цепочке

## 8. Как получаем сведения Windows

### ОС: build_os

Получаем модуль ntdll.dll через GetModuleHandleW, адрес RtlGetVersion через GetProcAddress и вызываем функцию через указатель. Здесь динамический вызов нужен, потому что функция не вызывается обычным прямым вызовом из подключённой библиотеки

Перед вызовом обнуляем расширенную структуру и записываем её размер. RtlGetVersion поддерживает базовую и расширенную структуру, выбирая её по dwOSVersionInfoSize. Расширенная даёт wProductType: workstation, server или domain controller. Сначала выделяем Windows Server, затем различаем клиентские Windows по major/minor/build. Для семейства major=10 текущая граница Windows 11 — build 22000; будущие семейства могут потребовать обновления таблицы названий. Числа версии выводятся отдельно, серверный выпуск по году не угадывается. [Документация структуры](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-osversioninfoexw), [RtlGetVersion](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-rtlgetversion)

Windows 11 тоже сообщает major=10 и minor=0. Это не ошибка

### Время: build_time и build_uptime

`GetSystemTime` — UTC, `GetLocalTime` — локальное время сервера. `SYSTEMTIME` хранит отдельные поля года, месяца, дня, часов, минут, секунд и миллисекунд. В ответе они форматируются в строку. Два последовательных вызова не являются атомарным снимком одного момента

Uptime не текущее время: это прошедшая длительность с запуска ОС. `GetTickCount64` возвращает миллисекунды. Делим на 1000 → секунды, на 86400 → полные дни. Остаток деления нужен, чтобы получить часы внутри суток, минуты внутри часа, секунды внутри минуты

Пример: 90061 секунда → 1 день, 1 час, 1 минута, 1 секунда. total_seconds — весь интервал, seconds — только остаток 0–59. После сна uptime может удивлять; это не время работы нашего exe

### Память: build_memory

`MEMORYSTATUSEX` обнуляется, dwLength задаётся sizeof структуры. `GlobalMemoryStatusEx` заполняет её. Выводятся загрузка в процентах и объёмы в байтах. Физическая память — RAM, виртуальное адресное пространство — не RAM и не размер установленной флешки. Большой total_virtual_bytes нормален для 64-битного процесса

1 GiB = 1024³ байт. Например 4294967296 байт = 4 GiB. available — доступно сейчас, меняется во время работы; нельзя требовать постоянного совпадения показаний

### Диски: build_drives и build_disk_space

`GetLogicalDrives` даёт битовую маску букв: A=бит0, B=бит1, C=бит2. Цикл i=0..25 проверяет каждый бит. Для найденной буквы формируем строку root вроде `C:\`

`GetDriveTypeA` определяет fixed/removable/network/cdrom/ramdisk/unknown. `GetVolumeInformationA` получает файловую систему. Если она недоступна, пишем unavailable. Это может быть пустой привод, а не сломанная вся программа

`i` — номер буквы, `count` — номер включённого в ответ диска, `used` — занятые байты текста. Поэтому C: может быть drive_0, хотя i=2. Буквы дисков не равны числу физических накопителей

`build_disk_space` оставляет только fixed и removable. `GetDiskFreeSpaceExA(root, NULL, NULL, &free_bytes)` получает общее свободное место тома; это не обязательно объём, доступный пользователю с квотой. Значение берём из free_bytes.QuadPart. Ошибка одного тома записывается в его поля, остальные тома продолжают обрабатываться

## 9. ACL: разбираем вывод, который ты показывал

### 9.1. Пять разных понятий

Security descriptor — описание безопасности объекта. В нём могут быть SID владельца, SID первичной группы, DACL, SACL и управляющие флаги

SID — идентификатор субъекта, например пользователя или группы. Имя — человекочитаемая подпись SID. ACL — список записей ACE. DACL относится к разрешению/запрету доступа; SACL используется для аудита и других security-механизмов, мы её не запрашиваем

ACE — одна запись: тип, субъект, маска доступа, флаги. Обычная allow ACE разрешает указанные права, deny ACE запрещает. Окончательный доступ рассчитывает Windows по токену субъекта и соответствующим правилам; наш вывод DACL — не вычисление effective permissions для выбранного пользователя

Владелец — отдельное поле descriptor, а не просто первая ACE. Поэтому GET_OWNER использует OWNER_SECURITY_INFORMATION, а GET_ACL — DACL_SECURITY_INFORMATION

Не говори «владелец находится внутри ACL»: методичка использует такое упрощение, но технически owner SID и DACL — разные компоненты security descriptor

### 9.2. SID и unresolved

Well-known SID имеют заранее известное значение. S-1-5-18 — LocalSystem, S-1-5-32-544 — группа Administrators, S-1-5-32-545 — Users, S-1-5-11 — Authenticated Users

`LookupAccountSidW` пытается получить имя и домен. Если SID не удаётся сопоставить с именем, остаётся `unresolved`, но сам SID всё равно выводится. Неизвестное имя не доказывает повреждение ACL: SID может относиться к специальной сущности или недоступной базе учётных записей

W-функция возвращает UTF-16; `WideCharToMultiByte(CP_UTF8, ...)` переводит имя в UTF-8. Клиент включает UTF-8 для консольного вывода. Пути объектов пока идут в A-функции, то есть полноценный единый Unicode-протокол путей не реализован: для демонстрации выбираем латинские пути

### 9.3. Весь build_acl по порядку

1. Проверяет путь: длину, ненулевой указатель, отсутствие встроенного нулевого байта
2. Копирует путь в локальный буфер и добавляет завершающий ноль
3. Если есть reg:, `registry_object_name` проверяет корень и убирает префикс. object_type становится SE_REGISTRY_KEY. Иначе требуется путь с буквой диска и обратным слешем, тип SE_FILE_OBJECT
4. Вызывает GetNamedSecurityInfoA и получает descriptor и указатель на DACL внутри него
5. Для файлового объекта GetFileAttributesA определяет, папка ли это. Это влияет на имена прав: FILE_READ_DATA или FILE_LIST_DIRECTORY
6. Если dacl=NULL, пишет dacl_state=null. Иначе GetAclInformation даёт AceCount
7. Цикл вызывает append_acl_ace для каждой записи
8. Освобождает descriptor через LocalFree. Указатель dacl после этого использовать нельзя

`append_acl_ace` получает запись через GetAce. Проверяет тип и минимальный размер, извлекает Mask и SidStart для обычных allow/deny ACE. Преобразует SID в строку, ищет имя, выводит поля и флаги, затем перебирает установленные биты маски. Для иных типов не пытается читать SID из неподходящей структуры, а пишет unsupported_N

### 9.4. Твой пример изменения прав

До добавления правила: ace_count=5. После: ace_count=6 и в начале появилась явная ACE:

```text
ace_0_type=allow
ace_0_sid=S-1-5-32-545
ace_0_name=Users
ace_0_flags=0x00
ace_0_mask=0x001301BF
ace_0_scope_self=yes
ace_0_inherited=no
```

Это разрешение Modify для группы Users на саму тестовую папку. Нулевые flags означают отсутствие флагов наследования; scope_self=yes потому, что INHERIT_ONLY не установлен

ACE не имеет постоянного ID `ace_0`: это индекс в текущем списке. Новая явная запись может стать первой, а старая первая уехать на индекс 1. Поэтому перенос старой Authenticated Users с ace_4 на ace_5 не означает, что именно эта ACE новая. Сравниваем субъект, тип, маску и флаги, а не один номер

Маска 0x001301BF включает биты 0,1,2,3,4,5,7,8,16,17,20. Для папки: LIST_DIRECTORY, ADD_FILE, ADD_SUBDIRECTORY, READ_EA, WRITE_EA, TRAVERSE, READ_ATTRIBUTES, WRITE_ATTRIBUTES, DELETE, READ_CONTROL, SYNCHRONIZE. Здесь нет WRITE_DAC и WRITE_OWNER — Modify не равен FullControl

### 9.5. Флаги наследования

| Бит флага | Имя | Как читать |
| --- | --- | --- |
| 0x01 | OBJECT_INHERIT_ACE | Передавать правило дочерним файлам |
| 0x02 | CONTAINER_INHERIT_ACE | Передавать дочерним контейнерам: папкам/ключам |
| 0x04 | NO_PROPAGATE_INHERIT_ACE | Ограничить дальнейшее распространение наследования |
| 0x08 | INHERIT_ONLY_ACE | Правило не действует на сам текущий объект, предназначено потомкам |
| 0x10 | INHERITED_ACE | Эта запись уже унаследована от родителя |

Например 0x13=0x10+0x02+0x01: inherited=yes, дети-файлы yes, дети-папки yes, self=yes. 0x1B дополнительно содержит 0x08: self=no. Это объяснение флагов, а не расчёт всех будущих ACL потомков. Подробности у Windows сложнее, особенно с generic-правами. [Правила наследования ACE](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules)

Для реестра выводим scope_child_keys и KEY_*: бит0 QUERY_VALUE, 1 SET_VALUE, 2 CREATE_SUB_KEY, 3 ENUMERATE_SUB_KEYS, 4 NOTIFY, 5 CREATE_LINK. Нельзя интерпретировать бит0 ключа как чтение файла

NULL DACL и пустая DACL различаются: NULL не ограничивает доступ средствами DACL; существующая пустая DACL не предоставляет разрешений через ACE. Есть отдельные правила владельца и привилегий, поэтому это не универсальное описание любых операций. Наш вывод отличает dacl_state=null от dacl_state=present с ace_count=0. [Null DACLs and Empty DACLs](https://learn.microsoft.com/en-us/windows/win32/secauthz/null-dacls-and-empty-dacls)

### 9.6. GET_OWNER и ошибки

build_owner проверяет тот же формат пути, запрашивает OWNER_SECURITY_INFORMATION, получает owner_sid, преобразует SID в строку и ищет Unicode-имя. В конце освобождает sid_text и descriptor

GetNamedSecurityInfo возвращает код ошибки непосредственно. Поэтому используем `error`, а не бездумно GetLastError после этого вызова. Ошибка 2 — объект не найден, 5 — доступ запрещён. Ошибка запроса не должна падать всем сервером; корректный error-ответ можно показать, затем выполнить пункт 5 в том же соединении

## 10. Шифрование: RSA, AES, IV и BLOB

### 10.1. Зачем два алгоритма

Симметричное шифрование: для encrypt/decrypt используется один секретный ключ. Здесь AES-256, ключ 256 бит = 32 байта, блок AES 16 байт. Быстро шифрует запросы и ответы

Асимметричная схема: публичный и приватный RSA-ключ. Публичную часть можно передавать, приватная остаётся у клиента. Здесь RSA-2048 используется для передачи AES-ключа, а не для шифрования каждого ответа с ACL

Последовательность соответствует методичке:

1. Клиент открывает CryptoAPI и генерирует RSA-пару
2. Клиент экспортирует PUBLICKEYBLOB и отправляет серверу type=100
3. Сервер импортирует публичный ключ клиента и генерирует случайный AES-256-ключ
4. Сервер экспортирует AES как SIMPLEBLOB, защищённый публичным RSA-ключом клиента с CRYPT_OAEP
5. Клиент импортирует SIMPLEBLOB, используя свой приватный RSA-ключ
6. Обе стороны теперь имеют AES-ключ и шифруют обычные сообщения

Новый клиент/новое соединение — отдельный сеансовый ключ. Отдельные server connection не делят один контекст

PUBLICKEYBLOB — сериализованный объект CryptoAPI с метаданными публичного ключа, SIMPLEBLOB — упакованный симметричный ключ. Наблюдавшиеся 276 и 268 байт — размеры BLOB, а не длины AES-ключа. Приватный RSA-ключ по сети не отправляется

### 10.2. Что такое IV

IV — initialization vector, вектор инициализации. Это 16 случайных байтов, задающих начальное состояние AES-CBC для конкретного сообщения. Это не пароль, не второй секретный ключ и не IP-адрес

Один и тот же AES-ключ используется в сеансе, но для каждого сообщения генерируется новый IV через CryptGenRandom. Поэтому одинаковый текст не обязан давать одинаковый шифротекст. Для CBC IV должен быть непредсказуемым; наш код использует генератор CryptoAPI

IV не требуется скрывать: получатель должен знать его для расшифрования. Поэтому он передаётся перед ciphertext. Без контроля целостности менять IV опасно: это не защита от активного вмешательства

CBC работает блоками. `CryptEncrypt(..., Final=TRUE, ...)` добавляет padding до полного блока; если длина уже кратна блоку, нужен ещё один блок padding. При decrypt он удаляется. Для наших внутренних 24 байт ciphertext=32, вместе с IV=48. Внешний заголовок ещё 24, итого 72 байта прикладного сообщения, без заголовков Ethernet/IP/TCP. [CryptEncrypt](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptencrypt)

Используем режим CBC провайдера по умолчанию; в коде KP_MODE явно не задаётся. Случайный IV задаём через CryptSetKeyParam(KP_IV)

### 10.3. Почему CryptDuplicateKey и memmove

Объект ключа CryptoAPI содержит не только секретные байты, но и рабочее состояние шифрования. Для каждого сообщения копируем session_key через CryptDuplicateKey, задаём IV на копии, шифруем/расшифровываем и уничтожаем копию. Исходный ключ сеанса сохраняется для следующего сообщения. [CryptDuplicateKey](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptduplicatekey)

Сервер шифрует ответ в том же send_buffer со смещением. Диапазоны могут перекрываться, поэтому перенос исходного текста сделан через memmove. IV устанавливается/сохраняется до перезаписи соответствующих байтов при decrypt

На encrypt заранее проверяется запас: 16 байт IV + до 16 байт padding. На decrypt проверяется наличие IV и хотя бы одного блока и кратность ciphertext 16. Это не проверка криптографической подлинности

### 10.4. Что шифрование доказывает и чего не доказывает

Threat model учебного показа — пассивный наблюдатель трафика: без ключа он не читает внутренние запросы, пути и ответы. В Wireshark видны внешние заголовки, IV, размеры и обмен публичным ключом

Отсутствуют аутентификация клиента/сервера, сертификаты, MAC/AEAD и полноценная replay-защита. Поэтому активный атакующий может пытаться подменять обмен ключами или менять ciphertext; проверка magic и структуры не заменяет криптографическую целостность. request_id связывает ответ с запросом, но не является полноценной replay-защитой

Attack surface — TCP-слушатель на всех IPv4-интерфейсах и обработчики входных BLOB/заголовков/путей. Доступ к локальным данным выполняется под учётной записью сервера, а не через авторизацию пользователя клиента. Сервер не impersonate-ит клиента. Если запустить от администратора и открыть порт недоверенной сети, информация может быть доступна любому умеющему выполнить наш handshake

Mitigation для учебной демонстрации: host-only-сеть, узкое правило firewall, не публиковать порт в интернет, не запрашивать секретные объекты, не заявлять промышленную защищённость. Добавление TLS/authenticated encryption — отдельная работа, не незаметная косметическая правка

## 11. IOCP без магии

IOCP = Input/Output Completion Port, порт завершения ввода-вывода. Это внутренняя очередь Windows, не TCP-порт 27015. В неё приходят уведомления о завершении асинхронного чтения/отправки. Worker thread — рабочий поток, который обрабатывает эти уведомления

Обычный блокирующий recv удерживает вызывающий поток до получения данных. В сервере post_receive запускает overlapped WSARecv и возвращается. Рабочий поток не обязан сидеть на одном клиенте; он ждёт общий IOCP и после завершения получает контекст нужного клиента. [I/O Completion Ports](https://learn.microsoft.com/en-us/windows/win32/fileio/i-o-completion-ports)

Важная тройка: SOCKET — канал, WSABUF — адрес и длина буфера, OVERLAPPED — состояние асинхронной операции. Пока операция выполняется, соответствующие данные должны оставаться существующими и пригодными для этой операции. Поэтому буферы находятся в connection, выделенной в heap, а не только в локальной переменной завершившейся функции

`WSA_IO_PENDING` означает, что операция успешно поставлена, но ещё не закончилась. В нашем режиме IOCP учитываем завершение через очередь и при немедленном успехе; не обрабатываем одно завершение дважды. [WSARecv](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsarecv)

У каждого соединения одновременно не более одной незавершённой операции. Это упрощает использование одного OVERLAPPED и смену operation=RECV/SEND. Разные клиенты могут обслуживаться параллельно, но запросы одного соединения идут последовательно

Состояния одного клиента:

```text
приём части HEADER -> весь HEADER -> приём PAYLOAD
-> обработка -> отправка части ответа -> весь ответ
-> снова приём HEADER
```

connection хранит:

| Поле/группа | Роль |
| --- | --- |
| socket | Принятое TCP-соединение |
| crypto | Ключи именно этого соединения |
| overlapped, wsabuf | Асинхронная операция и её буфер |
| operation | Сейчас чтение или отправка |
| receive_stage | Читаем HEADER или PAYLOAD |
| header_bytes, header_received | Байты и счётчик внешнего заголовка |
| request | Декодированный внешний заголовок |
| payload, payload_received | Тело и счётчик принятой части |
| send_buffer, send_length, send_completed | Постоянный ответ и прогресс отправки |
| peer | Строка IP:порт только для диагностики |

`CreateIoCompletionPort` сначала создаёт очередь. После accept второй вызов связывает принятый сокет с очередью и использует `(ULONG_PTR)client` как completion key. Затем GetQueuedCompletionStatus возвращает этот key, и worker восстанавливает connection*. Так он знает, чьё чтение завершилось

Если принято меньше необходимого, счётчик увеличивается и запускается чтение остатка. То же для отправки. Нулевое завершение чтения означает закрытие соединения другой стороной. При ошибке/закрытии close_connection освобождает ресурсы, когда у клиента нет другой незавершённой операции

Количество workers определяется GetSystemInfo, минимум 2. Число workers — не количество клиентов и не доказательство пропускной способности. Масштабирование через IOCP реализовано, но тысяча клиентов не была нагрузочно проверена

Ограничения: accept блокирующий, сбор информации внутри worker может блокировать, завершение Ctrl+C — остановка процесса без реализованного graceful shutdown. Нет лимита клиентов/таймаута простаивающих соединений, что важно для production/DoS, но не надо сейчас выдавать это за выполненные дополнительные механизмы

## 13. Демонстрация по методике, а не случайные клики

Подробные готовые команды — в короткой шпаргалке. Ниже объяснение, зачем шаги нужны

### 13.1. Два сервера и параллельные клиенты

Запусти сервер 1 в VM, сервер 2 на основной Windows. Открой два клиента к VM и один к localhost. Не выходи из первого, пока открываешь второй. Выполни запросы в обоих; сервер должен показывать отдельные peer с разными исходными портами

У одного клиента в пункте 1 будет ОС VM, у localhost — ОС хоста. Это показывает, что сведения реально получаются на разных машинах, а не захардкожены в клиенте. Одновременные живые соединения показывают совместное обслуживание; это не нагрузочный benchmark

### 13.2. Wireshark и обмен ключами

На основной Windows выбери интерфейс VirtualBox Host-Only, в твоей установке он отображался как Ethernet. Проверить соответствие можно Get-NetIPAddress. Начни capture ДО запуска нового клиента к VM, иначе не увидишь handshake

Display filter:

```text
tcp.port == 27015 && ip.addr == 192.168.56.101
```

Это фильтр отображения сверху, не capture filter возле интерфейса. Capture-filter имеет иной синтаксис. После подключения выбери пункт 1, затем останови захват красным квадратом

Начало TCP: SYN, SYN/ACK, ACK — установление транспортного соединения. Дальше BSI1 type=100 — обмен ключами, затем type=101 — защищённые кадры. ACK без Data не содержит прикладного ответа

Наблюдавшийся PUBLICKEYBLOB — 276 байт. Серверный ответ 292 прикладных байта = 24 заголовок + 268 wrapped BLOB. Запрос ОС: 24 внешний + 48 IV/ciphertext. Не привязывайся к номерам пакетов 29/33/70: в новом capture номера будут другими

Для полного сообщения: правой кнопкой по TCP-пакету → Follow → TCP Stream, при необходимости Show data as Hex Dump. Для отдельного сегмента можно выбрать Data в нижнем дереве. BSI1 в ASCII виден; status=ok/name=Windows внутри защищённого ответа не читаются. Не путай суммарную длину кадра Ethernet с TCP Len

Фраза на защите: «Открыты служебный внешний заголовок и IV. Публичный RSA-ключ передаётся открыто, AES-ключ — упакован RSA. Конкретный запрос и данные ответа находятся внутри AES-шифротекста»

Сохрани pcapng через File → Save As. Capture сам по себе не доказывает отсутствие MITM, MAC или replay-атак

### 13.3. Изменить права и показать новый результат

Меняем только отдельную тестовую папку, не C:\Windows и не профиль пользователя. Для новой репетиции на сервере 1 создаём C:\BSIT\Defense-ACL-Demo, сохраняем DACL через icacls /save. Запрашиваем пункт8 и фиксируем до. Команды изменения и восстановления выполняем в отдельном PowerShell VM от имени администратора: неповышенный icacls /restore может не иметь необходимых привилегий, даже если /grant уже сработал

В VM добавляем allow Modify для Users по SID. Заново выбираем пункт8 с тем же путём. Сравниваем ace_count и новую явную ACE по SID/mask/flags. Мы не добавляли сетевую команду изменения ACL: права меняются локально на сервере средствами Windows; наша программа только читает

После демонстрации восстанавливаем DACL через icacls /restore относительно родительской папки C:\BSIT. Не перезаписывай файл baseline после изменения, если хочешь вернуть исходные права. Команда /grant добавляет права; /grant:r заменяет явные разрешения соответствующего SID, поэтому для нашего показа используется /grant. [Документация icacls](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls)

На сервере 2 запроси C:\Windows или другую заранее подготовленную локальную папку. Права на одинаково названные пути двух серверов могут различаться

### 13.4. Флешка

Если сервер 1 в VM, одного подключения USB к ноутбуку недостаточно: накопитель надо передать гостевой системе через VirtualBox Devices/Устройства → USB, выбрав устройство. Сначала убедись, что нет записи на него на хосте; не форматируй и не очищай флешку

До подключения пункт6 показывает исходные тома. После передачи гостю дождись новой буквы в проводнике VM и снова пункт6 в том же клиенте. Новый drive_N_root и free_bytes показывают актуальное обнаружение. Пункт5 дополнительно покажет тип и filesystem

Некоторые USB-накопители Windows классифицирует как fixed; важен новый доступный том, а не обещание, что любое USB обязательно removable. Если в госте буква не появилась, программа не может её показать

Без физического устройства этот пункт остаётся незавершённым. Обсуди с преподавателем до защиты, а не имитируй проверку

## 14. Если что-то сломалось перед преподавателем

Сначала установи уровень проблемы: запуск/сборка → TCP → handshake → отдельный запрос. Не исправляй firewall, если ошибка на уровне отсутствующего exe

| Симптом | Проверка и действие |
| --- | --- |
| Сценарии отключены | Process-scope Bypass, затем build_stage1.ps1 |
| Permission denied при линковке exe | Выйти из всех клиентов 0, сервер Ctrl+C, повторить сборку |
| Имя exe не распознано | Get-Location, Test-Path; правильный путь и префикс .\ |
| Cannot connect:10061 | Нет слушателя или активный отказ; проверить сервер/IP/порт |
| Cannot connect:10060 | Таймаут; проверить маршрут, адаптер host-only и firewall |
| TCP true, а меню нет | Проверить актуальность обоих exe, обмен ключами, лог сервера |
| Зависла консоль с «Выбрать/Select» в заголовке | Esc снимает выделение; перед сдачей отключить QuickEdit в свойствах старой консоли |
| Нет connection log у нужного сервера | Клиент подключается к другому IP/порту или трафик не дошёл |
| Сервер не слушает 27015 | Проверить занятый порт и полный путь уже запущенного процесса |
| win32_error=2 | Путь не существует НА СЕРВЕРЕ; регистр корня реестра и формат пути |
| win32_error=5 | Учётной записи сервера не хватает доступа; выбрать тестовый объект, не выдавать всем доступ к системной папке |
| path_must_be_absolute | Ввести C:\..., без кавычек и прямых слешей |
| invalid_registry_path | reg:CURRENT_USER\... или другой поддерживаемый корень |
| owner_name=unresolved | SID найден, имя не разрешилось; объяснить и проверить SID, не паниковать |
| В capture нет обмена ключами | Начать захват, затем НОВОЕ соединение клиента |
| В capture только SYN | Нет TCP-подключения; это ещё не обмен ключами |
| Добавленная ACE поменяла индекс других | Нормальная перестановка; сравнить SID/type/mask/flags |
| VM показывает 2 workers | Нормально при двух доступных процессорах; версию проверить SHA256 |

Test-NetConnection проверяет только TCP-handshake. Он сам не выполняет BSI1, поэтому после проверки сервер может написать connect/disconnect без request. Отрицательный ping отдельно не доказывает недоступность TCP: ICMP могут фильтровать

Полезный порядок проверки VM: сервер виден локально по 127.0.0.1 → виден в VM по её host-only-IP → доступен с хоста → настоящий клиент выполняет handshake и пункт1. Не отключай весь Windows Firewall ради одного порта

## 15. Мини-защита: вопросы и ответы

Сначала закрой ответы и проговори своими словами. Если можешь только читать с листа, подготовка ещё не закончена

1. Что делает лабораторная? Клиент собирает сведения от серверных агентов Windows через свой защищённый протокол TCP
2. Почему центральная программа называется клиентом? Она инициирует соединения и запросы; серверы на наблюдаемых машинах принимают их
3. Почему сервер stateful? У каждого соединения ключ, buffers, счётчики и этап операции сохраняются между вызовами
4. Чем socket отличается от IP и порта? IP/порт адресуют endpoint, socket — ресурс/дескриптор программы для обмена
5. TCP гарантирует одно сообщение на recv? Нет, это поток; дочитываем точную длину из framing
6. Зачем 24-байтный заголовок? Определить тип, ID и длину тела, проверить версию и magic
7. Зачем request_id? Связать ответ с запросом и проверить согласованность внутренних/внешних кадров, не «доказать личность»
8. Почему заголовок не отправляем как struct? Padding, endian и ABI; ручная сериализация задаёт фиксированный формат
9. Зачем два заголовка? Внешний framing позволяет читать ciphertext, внутренний описывает конкретный запрос и защищён вместе с телом
10. IOCP — это порт 27015? Нет, очередь завершённых I/O внутри Windows
11. Где реальная асинхронность? WSARecv/WSASend с OVERLAPPED и GetQueuedCompletionStatus у workers
12. WSA_IO_PENDING — ошибка? Нет, успешно начатая незавершённая операция
13. Зачем connection? Постоянная память для состояния одного клиента и асинхронных buffers
14. Почему нельзя передать исчезающий локальный buffer в WSASend? Отправка может закончиться после возврата функции, Windows ещё использует данные
15. Один поток на клиента? Нет, общий pool workers обслуживает завершения разных клиентов
16. AcceptEx реализован? Нет, accept блокирующий; IOCP работает на принятых соединениях
17. Откуда числа памяти? GlobalMemoryStatusEx на стороне сервера, не на клиенте
18. Uptime и текущее время одинаковы? Нет, длительность с запуска ОС и календарный момент
19. Почему Windows11 major10? Номер версии ядра не равен маркетинговому имени; проверяем build и product type
20. Почему C: это drive_0? count нумерует найденные тома, а i=2 — позиция буквы в маске
21. Чем ACL отличается от ACE? ACL — список, ACE — запись списка
22. Владелец — первая ACE? Нет, owner SID — отдельное поле security descriptor
23. Что такое SID? Системный идентификатор субъекта, имя — разрешаемая подпись
24. Зачем well-known SID? Узнаваемые стандартные субъекты независимо от локализованного имени, например Administrators
25. Что такое наследование? Передача ACE дочерним объектам по флагам; inherited и inherit-only — не одно и то же
26. Почему биты реестра называются иначе? Нижние specific rights зависят от типа объекта
27. Значит ли allow в одной ACE, что пользователь точно имеет доступ? Нет, effective access зависит от токена, других записей и правил Windows
28. Какова структура списков контроля доступа? Security descriptor содержит DACL/SACL; ACL содержит header и последовательность ACE; ACE имеет тип, flags, size и зависящие от типа поля
29. Как передаётся сеансовый ключ? Клиент отправляет public RSA, сервер создаёт AES и заворачивает public RSA, клиент раскрывает private RSA
30. Преимущество сеансового ключа? AES быстро шифрует большие сообщения, RSA используется только для передачи небольшого ключа
31. Что такое IV? Случайное начальное значение CBC, отдельное для сообщения, открыто перед ciphertext
32. 268 байт — размер AES-ключа? Нет, размер упакованного BLOB; AES-256 ключ 32 байта
33. Зачем копировать ключ? CryptoAPI хранит рабочее состояние; отдельная копия на сообщение изолирует его
34. Что видно в Wireshark? TCP-метаданные, внешний BSI1, публичный ключ, wrapped BLOB, IV и ciphertext; внутренний текст скрыт
35. Есть аутентификация и целостность? Нет, это учебное шифрование, не полный защищённый канал
36. Под чьими правами читаются объекты? Под учётной записью сервера; клиентская авторизация/impersonation отсутствует
37. Что делают тесты? Protocol проверяет сериализацию, crypto — обмен ключами и двусторонний AES round-trip; живые сетевые/VM-проверки отдельны
38. Почему 0/ошибка Windows не всегда одно и то же? API имеют разные контракты; GetNamedSecurityInfo возвращает код, BOOL API — успех/неуспех
