# БСИТ — лабораторная работа № 1

Учебная клиент-серверная программа на C для получения сведений о Windows-машине. Сервер запускается на исследуемом компьютере (в том числе в VirtualBox), клиент подключается к нему по TCP и отправляет запросы. Приём и отправка данных на сервере обрабатываются через Windows I/O Completion Ports (IOCP).

> Это лабораторный стенд, а не готовое средство удалённого администрирования. Не открывайте его порт в Интернет: ограничения безопасности перечислены ниже.

## Возможности

| Пункт меню | Запрос | Что возвращает сервер |
| --- | --- | --- |
| `1` | `GET_OS` | название и версию Windows |
| `2` | `GET_TIME` | текущее время |
| `3` | `GET_UPTIME` | время работы системы |
| `4` | `GET_MEMORY` | загрузку, общий и доступный объём памяти |
| `5` | `GET_DRIVES` | подключённые диски и файловые системы |
| `6` | `GET_DISK_SPACE` | свободное место на локальных и съёмных дисках |
| `7` | `GET_OWNER` | владельца файла, каталога или ключа реестра |
| `8` | `GET_ACL` | DACL и отдельные записи ACE для того же объекта |

Для пунктов `7` и `8` клиент запросит путь **на сервере**, например `C:\Users\Public` или `reg:CURRENT_USER\Software`. Для реестра также поддерживаются корни `MACHINE`, `USERS` и `CLASSES_ROOT` после префикса `reg:`. Сведения относятся к компьютеру и учётной записи, под которой работает сервер, а не клиент.

## Сборка и тесты

Нужны Windows, CMake 3.20+, компилятор C11 (MinGW или MSVC) и соответствующий генератор CMake. На машине, для которой написан проект, удобнее использовать `build_stage1.ps1`: скрипт создаёт junction с путём без кириллицы, собирает программы и запускает CTest. **Пути к CLion/MinGW/CMake/Ninja в начале скрипта заданы для конкретной машины** — на другом компьютере их нужно изменить.

Из PowerShell в папке проекта:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
.\build_stage1.ps1
```

Настройка `ExecutionPolicy` действует только в текущем окне PowerShell. Скрипт печатает полные пути к `lab_server.exe` и `lab_client.exe`; обычно они находятся в `build-ok`. Junction `C:\Users\<имя>\bsit_lab1_workspace` ссылается на исходную папку проекта, а не создаёт вторую копию.

Если проект уже расположен в пути без кириллицы и инструменты сборки доступны через `PATH`, можно использовать обычный CMake с Ninja:

```powershell
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
```

Есть два автоматических теста: `protocol_tests` проверяет сетевой заголовок, `crypto_tests` — обмен ключом и шифрование/расшифрование. Они не заменяют ручную проверку клиента и сервера на двух машинах.

## Быстрый запуск

В первом окне PowerShell запустите сервер:

```powershell
.\build-ok\lab_server.exe
```

Во втором окне запустите клиент:

```powershell
.\build-ok\lab_client.exe 127.0.0.1
```

Сервер слушает TCP-порт `27015`. После строки `Key exchange complete` выберите номер запроса, например `4` для памяти. Завершение клиента — пункт `0`; сервер останавливается через `Ctrl+C`. Если программы собраны обычным CMake, используйте его каталог сборки вместо `build-ok` (у многоконфигурационных генераторов `.exe` может лежать в `Debug`).

Другой порт задаётся первым аргументом серверу и вторым клиенту:

```powershell
.\build-ok\lab_server.exe 29001
.\build-ok\lab_client.exe 127.0.0.1 29001
```

### Запуск с виртуальной машиной

1. Настройте в VirtualBox **Host-only Adapter** для связи хоста с VM; отдельный NAT-адаптер можно оставить для Интернета внутри VM.
2. Узнайте IPv4-адрес VM через `ipconfig`. Например, при адресах хоста `192.168.56.1` и VM `192.168.56.101` они должны находиться в одной host-only сети. Адрес вида `169.254.x.x` означает, что нужный адрес не был получен; сначала исправьте настройку сети.
3. Перенесите **свежесобранный** `lab_server.exe` в VM и запустите его там. Разрешите входящий TCP-порт в брандмауэре только для нужной частной/host-only сети.
4. На хосте запустите `.\build-ok\lab_client.exe 192.168.56.101` (подставьте фактический адрес VM). Подтверждение работы — `Key exchange complete` у клиента и строки `[connect]`, `[key exchange]`, `[request]` у сервера. `Test-NetConnection` проверяет лишь TCP-подключение, а не наш протокол.

## Что происходит в сети

При каждом новом соединении клиент отправляет открытый RSA-ключ. Сервер создаёт случайный сеансовый ключ AES-256 и возвращает его в зашифрованном виде. Затем несколько запросов и ответов идут по тому же TCP-соединению с одним сеансовым ключом; для каждого сообщения создаётся новый IV.

У прикладного протокола есть 24-байтный заголовок с сигнатурой `BSI1`, версией, типом кадра, `request_id` и длиной тела. Тип `100` обозначает обмен ключом, тип `101` — защищённый кадр. Внешний заголовок виден в сети, но внутренний тип запроса (`GET_MEMORY`, `GET_ACL` и т. д.) и содержимое ответа находятся внутри шифрования. TCP может разбить один кадр на несколько пакетов, поэтому одна строка Wireshark не обязательно равна одному запросу.

Для демонстрации в Wireshark начните захват на host-only интерфейсе **до** запуска клиента и примените фильтр отображения:

```text
tcp.port == 27015 && ip.addr == 192.168.56.101
```

Замените IP на адрес вашей VM. В консоли клиента после пункта `4` будет видно, например, `available_physical_bytes`; в захвате ответа это число открытым текстом не отображается, поскольку клиент печатает его уже после расшифрования.

## Ограничения безопасности

Шифрование скрывает содержимое запросов от пассивного наблюдателя, **но само по себе не подтверждает личность сервера или клиента**. В текущем протоколе нет взаимной аутентификации, контроля целостности сообщений и защиты от повторного воспроизведения. Активное вмешательство в обмен находится вне модели защиты этой учебной реализации. Приём новых соединений выполняется обычным `accept()`, тогда как IOCP используется для приёма и отправки данных уже подключённых клиентов.

Используйте проект только в изолированной учебной сети. Для реального применения потребовались бы аутентификация сторон и стандартный протокол защищённого транспорта (например, TLS), а также ограничение доступа к собираемым сведениям.
